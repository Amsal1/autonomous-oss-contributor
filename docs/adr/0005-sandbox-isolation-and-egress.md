# ADR-0005: Sandbox isolation via per-stage profiles, a split coder, per-task internal networks, and a squid allowlist
Status: Accepted (revised in design rev 1, rev 2 and rev 3) · Date: 2026-10-17 · Design: DESIGN.md §10, §11

## Context
The coder must run hostile repo code (tests, install scripts) and kiro-cli needs a Kiro key. Hostile code at the same UID can read the key from `/proc/<pid>/environ`, and "Kiro hosts give an attacker no readable channel" is unverified (server-side web tools, remote MCP, cloud sessions). A hostile repo can also ship `.kiro/` workspace config (MCP servers, hooks). IP allowlists are brittle for CDN-fronted hosts.

## Decision
- Stages run in throwaway containers (UID 10001, `--cap-drop ALL`, `no-new-privileges`, read-only rootfs, default seccomp, limits, per-task volume, no host mounts, `--pull never`, `--dns 127.0.0.1`), created only through the Docker API filter (ADR-0001).
- **Invariant: no container both holds a credential and executes repo code.**
  - `fetch`/`validate`/`package`: run repo code or git on repo data; no secrets.
  - `research` (vetter, planner, reviewer, summarizer): Kiro key + public web (summarizer: no web), tools `read`/`web_*` only, repo read-only.
  - Coder = `agent-llm` (key, kiro-cli, tools `read`, `write` on `/work/repo/**`, `@ossbot-exec/run`; no shell; Kiro-only egress) + `agent-exec` (no key, `--network none`, deterministic `ossbot-execd` running commands with a fixed env). kiro-cli is not even installed in code-running images.
  - All kiro-cli processes use a tmpfs HOME and an empty tmpfs cwd, never the repo, so repo-local `.kiro/` config is not loaded.
- Single-container coder mode exists only as an audited downgrade, refused unless an ADR addendum proves no attacker-directed egress via Kiro features and env scrubbing by `kiro-cli --sandbox`.
- sandboxd scans every output, log, and bundle blob for the literal key and its encodings before publishing (fail + pause); the gatekeeper hash-checks token-like strings against the key hashes.
- Each task/profile has its own `--internal` network with a persisted /28; the proxy (10.212.0.2 on `ossbot-egress`) is attached with alias `proxy`; squid selects the profile by source subnet and matches CONNECT host names (no TLS interception). Host users get one proxy port each (runner 3140, Hermes 3141, gatekeeper 3150 limited to Telegram + GitHub) enforced by owner-match iptables; no direct 443/53 for any service user.

## Alternatives
- Key and hostile code in one container with Kiro-only egress (v1): rejected (review H3).
- TLS-intercepting proxy to allow fetch but not push: rejected for complexity and CA distribution.
- Kiro local command sandbox as the primary control: unverified inside containers; only relevant to the downgrade mode.

## Revision 2 amendments (design review round 2)
- H1: the coder's built-in `read`/`write` and research's read-only task-volume mount are replaced. Key-holding containers never mount an attacker-writable path. Research reads a symlink-free snapshot volume, and `agent-llm` has no `/work` mount and uses `@ossbot-exec/*` file tools. Denies are extended to `/proc`, `/sys`, `/dev`, `/run`. See ADR-0017.
- M2: live probes gate Kiro jobs per (CLI, image, agent config, settings, trust mode) tuple (ADR-0017).
- M3/M4: stage I/O at image-rooted `/io/input` (read-only, filled by a `stage-in` container) and `/io/output`; complete Docker filter create allowlist.
- M6/M7: firewall split into `ossbot-firewall` (before Docker) and `ossbot-firewall-docker` (`BindsTo`/`PartOf` Docker), own chains, `ExecStartPre --check` on every service (fail closed); proxy DNS allowed to the WSL resolver only.
- **Addendum slot (implementation):** result of "does Kiro `read` resolve symlinks before matching `deniedPaths`?" (DESIGN §23 5a). Not load-bearing after H1.

## Revision 3 amendments (design review round 3, M2/M11/N5)

- M2: a fresh named volume takes its root owner and mode from the image directory (copy-up). So the writable mountpoints `/work`, `/work/repo`, `/io/output`, `/run/exec`, `/snap` and `/home/agent` are created `10001:10001 0700`, and `/io/input` and `/in` stay `root 0755`. The read-only rootfs, not ownership, is what prevents mountpoint swaps.
- M2: Docker mounts every tmpfs `noexec` unless `exec` is given. `/tmp` gets `exec` only in the code-running profiles (fetch, validate, agent-exec, package), and the Docker filter enforces that profile set. LLM profiles keep `noexec`. If kiro-cli is proven to need exec, the only allowed change is `exec` on `/tmp` for the LLM profiles, recorded here with probe evidence. Sandbox test S-perm-1.
- M11: new `catalog` profile for `list_models` only: `sandbox-llm`, `repo_mode none`, no inputs, network from the `agent-llm` pool (`kiro_core` only). It is exempt from the probe gate (ADR-0017).
- N5: the Docker filter refuses container start, not only create, while killed or paused.
- **Addendum slot (implementation):** whether kiro-cli needs exec under `/tmp` or `$HOME` (DESIGN §23 5), and the Docker 29 copy-up ownership result (§23 14).

## Consequences
Two containers per implement run and an MCP relay to maintain. The coder has no web tools in v1 (planner does the research). **Verify:** exact V3 tool ids and MCP tool naming, workspace config discovery rules (S-ws-1), Kiro host set via learn mode, whether web tools are server-side.

## Implementation addendum (FEAT-003, 2026-10-17): DESIGN §23 items 14 and 16

Checked by web search and a live probe on the `ossbot` distro before the firewall and squid renderers were written. Items marked "pending live probe" need Docker, which FEAT-004 installs; the sandbox smoke tests there (S-perm-1, stage-in, `test_proxy_dns.sh`) close them.

Docker 29 (item 14):
- Firewall backend. iptables is still the default in Docker 29; nftables support (since 29.0.0) is experimental and has **no `DOCKER-USER` chain** ([Docker with nftables](https://docs.docker.com/engine/network/firewall-nftables/)). Decision: `daemon.json` sets `"firewall-backend": "iptables"` explicitly, so `OSSBOT-FWD` can hook `DOCKER-USER`. FEAT-004 checks `iptables -S DOCKER-USER` after the daemon starts.
- Host to an unpublished port on a user bridge. Docker documents that every port of a container on a bridge network is reachable from the Docker host ([Networking overview](https://docs.docker.com/engine/network/)). The proxy therefore runs without published ports; the `-p 10.212.0.1:<port>` fallback is not used. Pending live probe.
- Embedded DNS. The embedded resolver forwards non-container names from the **container's** network namespace; only a loopback upstream taken from the host's `resolv.conf` is forwarded from the host namespace, and since 25.0.5/26.0.0 containers attached only to internal networks get no external forwarding at all ([GHSA-mq39-4gv4-mvpx / CVE-2024-29018](https://github.com/moby/moby/security/advisories/GHSA-mq39-4gv4-mvpx)). An explicit `--dns` makes forwarding happen from the container namespace. So with `--dns 127.0.0.1` the upstream is the sandbox's own loopback, where nothing listens: external names never resolve. Content was rephrased for compliance with licensing restrictions.
- Resolver placement (live probe, 2026-10-17): `/etc/resolv.conf` is WSL-generated with `nameserver 10.255.255.254`, and that address is assigned to the distro's `lo` (`inet 10.255.255.254/32 scope global lo`). Packets from the proxy (10.212.0.2) to it arrive over the bridge and traverse the host **INPUT** chain, not FORWARD. The two `OSSBOT-IN` ACCEPT rules (UDP/TCP 53 from 10.212.0.2/32 to `<NS>/32`) are therefore load-bearing and are rendered before both DROPs. squid uses `dns_nameservers <NS>` directly, never Docker's embedded resolver, for external names.
- Copy-up ownership. moby copies the image mountpoint's owner, group and mode onto a fresh, empty named volume at first mount ([moby#35486](https://github.com/moby/moby/issues/35486)); this is what the M2 directory owners in the Dockerfiles rely on. Pending live probe S-perm-1 (both the rw-first and the `ossbot-ro-*` snapshot-first case).
- Archive PUT into a created container. Extraction into a writable volume mountpoint of a container with a read-only rootfs is supported; the known failure is only a symlinked parent directory ([moby#43015](https://github.com/moby/moby/issues/43015)), which `/in` is not (image-rooted directory). `docker cp` stats the destination with `HEAD /containers/{id}/archive?path=…` before the PUT, so the filter allows `HEAD` with exactly the same checks as the matching `PUT`/`GET` row. Pending live probe and the corpus re-recording (§23 item 15).
- Image store. Fresh Docker 29 installs use the containerd image store ([containerd image store](https://docs.docker.com/engine/storage/containerd/)), so locally built images carry a content digest and the `ossbot/<image>@sha256:<digest>` form works with `--pull never`. FEAT-004 records the digests and confirms a run by digest.
- `--workdir` inside a tmpfs (`/home/agent/cwd`): pending live probe. `kiro.sh` and `list_models.sh` also `mkdir -p` and `cd` into it themselves, so the result only decides whether Docker creates it.
- `exec` in `--tmpfs` options is passed explicitly (Docker adds `noexec,nosuid,nodev` otherwise); pending live probe S-perm-1.

Squid 6 (item 16):
- Version: Ubuntu 24.04 ships `squid 6.14-0ubuntu0.24.04.4` (noble-updates, `apt-cache policy squid` on the distro). The proxy image pins that package version.
- Listeners and ACLs: `http_port <ip>:<port>` binds only that address. The `localport` ACL matches the TCP port the client connected to, and `myportname` matches the `name=` of an `http_port` line (both "fast" ACLs, [squid acl reference](https://www.squid-cache.org/Doc/config/acl/)). The renderer names every listener (`name=sandbox|runner|hermes|gatekeeper`) and matches with `myportname`, plus `src` ACLs: per-profile source pools on 3128 and `src 10.212.0.1/32` on the host ports. Requests on 3128 from 10.212.0.1 are denied.
- Interface limit: no per-container limit on attached networks is documented. The often quoted limit of about 30 networks comes from default-address-pool exhaustion, which does not apply because every ossbot network has an explicit /28. Expected attachments of the proxy: 2 pipelines × 3 task networks + catalog ≈ 7. FEAT-004's smoke test attaches 10 networks. Pending live probe.
- Log format: the rendered `logformat ossbot %ts.%03tu %>a %>lp %Ss/%03>Hs %rm %ru %<a` records the client address (source subnet, hence profile and task), the local port (caller class), the result and the requested host. The squid log parser (Phase 2 anomaly) keys on `%>a` and `%>lp`.
- Kiro hosts in `kiro_core` are unchanged; learn mode (§11.3) still has to pin them once a key exists.
- The rendered `squid.conf` was parsed by the real squid 6.14 binary (`squid -k parse`, package extracted to a temp dir, not installed): every `acl` and `http_access` line accepted; the only warning is the RFC note for `via off`.

iptables (live format probe): the distro's `iptables` is 1.8.10 (nf_tables). Each rendered chain was loaded into an unreferenced scratch chain and read back with `iptables -S`/`ip6tables -S` (no jump, no traffic effect, removed afterwards). Output adds `-m udp`/`-m tcp`, `/32` on addresses and `--reject-with icmp-port-unreachable`; `ossbot-firewall --check` normalizes exactly these and treats any other token as drift.

Implementation decisions (FEAT-003), each stricter than or equal to the design text:
- Output key scan of bundles (§10.6): a package bundle is a thin pack whose prerequisite (the round base) sandboxd does not have, so `git bundle unbundle` into an empty repo fails for every fix round. sandboxd inflates every pack entry itself instead: whole objects in full, deltas by their literal insert data (the only place new bytes can be). Unparseable bundles fail the stage (`bundle_unreadable`).
- Docker filter: `HEAD /containers/{id}/archive` is allowed with the same checks as the matching `PUT`/`GET` row (the CLI stats before copying). The image is bound to the profile (`sandbox-llm` only for research, agent-llm and catalog; `sandbox-full` otherwise), `/in` only for stage-in and `/snap` only for snapshot. `AttachStdout`/`AttachStderr` booleans and `ConsoleSize: [0, 0]` are accepted because `docker create` sends them; the attach endpoint stays forbidden.
- The digest allowlist comes from a root-owned copy of `versions.lock.yaml` at `/etc/ossbot/versions.lock.yaml` (written by the provision `images` step), because image digests are not part of the four-file config snapshot. Missing or `pending` digests allow no image.
- Job args reach the fixed entrypoints as `OSSBOT_ARG_*` environment values (the filter binds `Cmd` to the bare script path); `package.sh`/`unbundle.sh` read them as defaults for their flags.
- `agent-exec` writes its `exec-log.jsonl` to its own output volume `ossbot-out-<run_id>-exec`; package outputs go to `/srv/ossbot/artifacts/<cid>/<rev>/` (the JobSpec package args carry `rev`).
- ip6tables: `OSSBOT-OUT` (per service uid: `lo` accept, else DROP) and `OSSBOT-FWD` in `FORWARD` (DROP on `docker0`/`br-+`), in the host part.
- `policy.yaml sandbox.kiro_trust_mode` (`ids` | `all`, default `ids`) added to the schema, read by sandboxd from the snapshot.

## Implementation addendum (FEAT-004, 2026-10-18)
Live probes on Docker 29.9.1 (containerd image store, iptables backend) on the provisioned distro, DESIGN §23 items 14-16:
- Corpus re-recorded from the pinned CLI (`tests/unit/dockerfilter/record_corpus.py` -> `corpus/recorded.json`, fake Docker API on a temp socket). Differences from the hand-built model, fixed in `sandboxd/runtime/cli_model.py` and asserted by `test_recorded_corpus.py`: `HostConfig.MemorySwappiness` is `-1` (the filter accepts only `null` or `-1`), `HostConfig.Dns` is `null` without `--dns`, `Mounts[].ReadOnly` is omitted when false, `OnBuild` is absent, `NetworkingConfig.EndpointsConfig` is `{}` (no endpoint entry for `--network`), `Env` is not in flag order. `AttachStdout`/`AttachStderr` are `true` only for `docker create` (stage-in). `docker run --detach` sends `POST wait` (no condition) then `start`; `docker network rm` first sends `GET /networks/<name>` (filter route `networks/inspect` added, same checks as delete); `docker cp -` sends `HEAD` then `PUT ...archive?noOverwriteDirNonDir=true&path=/in`; `docker rm -f -v` sends `force=1&v=1`; `docker ps` sends `all=1&size=1` with the label filter. The filter allows every recorded request.
- Copy-up (S-perm-1): a fresh named volume takes the image directory's owner and mode (`/io/output` 10001:0700); the snapshot volume filled rw at `/snap` and then mounted read-only at `/work/repo` works; execd binds `/run/exec/exec.sock`; validate executes `/tmp/bin/x` (`exec` tmpfs option honoured); research, agent-llm and catalog get EACCES (`noexec`).

- PUT archive into a created, never-started container with a read-only rootfs works: stage-in inputs arrive as regular 0444 files identical to the sources, and a hostile job's `/work/input` and `/work/output` symlinks change nothing for the next job.
- The proxy was attached to 10 task networks at once (11 networks) and kept resolving. An internal-network sandbox with `--dns 127.0.0.1` resolves nothing, also not via 127.0.0.11. A subnet outside every squid pool gets 403.
- The `research` profile's egress includes `web_public`, so `https://example.com` via the proxy is 200 there and 403 for every other profile, as §11.3 specifies.
- Host access to the unpublished proxy ports on the user bridge works (no `-p` fallback); the §11.4 per-uid matrix is verified by `tests/system/test_egress_per_uid.sh`.

## Implementation addendum (Phase 1 review P1-1, 2026-10-18): no DNS through `lo`
The Phase 1 review probed a raw DNS query from each service uid to the WSL resolver `10.255.255.254:53` and got answers for all five accounts: the resolver sits on `lo`, and `OSSBOT-OUT` accepted every `-o lo` packet for those uids. That was a direct DNS channel past squid, contradicting §11.4 ("no user gets direct UDP 53").
- **Decision:** every service uid (`ossrunner`, `hermes`, `gatekeeper`, `ossbox`, `ossnobody`) now gets `-p udp --dport 53 -j REJECT` and `-p tcp --dport 53 -j REJECT` as its first two `OSSBOT-OUT` rules, ahead of the proxy-port and `lo` ACCEPTs (ip6tables: the same two rules with `DROP`). The rules have no `-d`, so they cover every resolver address (resolv.conf nameservers, a `127.0.0.53` stub, any future address) without tracking it. No service needs host-side name resolution: HTTP goes through the proxy by IP literal, and the proxy's own DNS is the `OSSBOT-IN` ACCEPT pair (unchanged).
- `--check` needed no new normalization (`-m udp`/`-m tcp` and the default `--reject-with` were already folded). The golden render, DESIGN §11.4 and `test_render.py` (DNS refusal precedes the `lo` ACCEPT for every uid in both families) were updated.
- `tests/system/test_egress_per_uid.sh` and doctor's per-uid egress check now also send UDP and TCP queries for `example.com` to every resolv.conf nameserver and `127.0.0.53`, as every service uid, and expect no answer; the system test also checks that root still gets an answer (control).

## Implementation addendum (Phase 1 review P1-6, 2026-10-18): systemd-resolved masked
The round-2 review found a second DNS channel that the port-53 rules cannot see. systemd-resolved (systemd 255 on Ubuntu 24.04) was active; its varlink socket `/run/systemd/resolve/io.systemd.Resolve` is `0666` and its D-Bus API `org.freedesktop.resolve1` is open to every local user. A `ResolveHostname` request is a unix-socket or bus message, and resolved then queries upstream as uid `systemd-resolve`, which has no owner rule in `OSSBOT-OUT`. Every service uid resolved arbitrary (attacker-chosen) labels this way: enough for DNS tunnelling. Sandbox containers were not affected (`--dns 127.0.0.1` on `--internal` networks, no `/run` mounts).
- **Decision:** provision step `firewall` runs `systemctl disable --now` and `systemctl mask systemd-resolved.service` (idempotent, prints changed/unchanged). Nothing in the distro needs resolved: `/etc/resolv.conf -> /mnt/wsl/resolv.conf` names only the WSL resolver `10.255.255.254`, nsswitch is `hosts: files dns`, and root/ossadmin (and the proxy via the `OSSBOT-IN` pair) resolve directly. Masked, the bus name cannot be D-Bus-activated either (`Unit dbus-org.freedesktop.resolve1.service not found`). A restrictive D-Bus policy was rejected: it would not cover varlink.
- **Enforcement:** `ossbot-firewall --check` (host part) also fails with `firewall_drift:resolved_ipc` when `/etc/systemd/system/systemd-resolved.service` is not a symlink to `/dev/null` or the varlink socket accepts a connection (a stale socket file without a listener is fine). So every unit's `ExecStartPre` fails closed, the watchdog soft-kills with reason `firewall_drift:resolved_ipc` (e.g. after an apt upgrade or a manual unmask), and doctor reports FAIL (`check_firewall` plus a separate `systemd-resolved masked` line).
- **Probes:** `tests/system/test_egress_per_uid.sh` and doctor's per-uid egress check send `ResolveHostname` over varlink and over D-Bus (`busctl`) as each of ossrunner, hermes, gatekeeper, ossbox and ossnobody and expect no answer; the system test also checks the unit is masked and inactive, and root still resolves via `10.255.255.254` (control). Verified live after the change: `systemctl is-enabled` = `masked`, `busctl` as ossbox fails, `getent hosts github.com` as root still answers.

## Implementation addendum (Phase 1 review P1-11/P1-12, 2026-10-18): squid never resolves for a denied request
Round 3 found that squid itself was the remaining DNS path. `dstdomain` without `-n` matched an IP-literal request through its PTR name (P1-11: an attacker IP with a PTR of `runtime.us-east-1.kiro.dev` passed `cat_kiro_core`), and the global `http_access deny denied_dst` resolved every requested name before any category check (P1-12: DNS exfiltration through 403'd requests on 3140, 3150 and the fetch and llm pools).
- **Decision (template `sandbox/proxy/squid.conf.j2`):**
  - Every name ACL is `-n`: `dstdomain -n` for the categories and `denied_domains`, `dstdom_regex -n -i` for the new `ip_literal` ACL. With `-n`, squid never converts between an IP and a name, so an IP literal can only match an IP entry, and no category has one.
  - `http_access deny ip_literal` sits ahead of every allow, on every port, including the `web_public` callers (research pool, hermes 3141). Its patterns (`render.IP_LITERAL_PATTERNS`) cover every numeric form getaddrinfo accepts (dotted, short, decimal, octal, hex) and IPv6 with or without brackets. Squid canonicalizes numeric hosts (`3405803786` and `0xcb.0.0x71.0xa` are logged as `203.0.113.10`), and the pattern still matches the canonical form. DESIGN §11.1 already matches CONNECT *host names*. A `web_public` caller that wants a raw IP now gets 403, which nothing in v1 needs.
  - The resolved-IP deny moves from a global deny line to the end of each allow line: `http_access allow port_X <src> <cat_Z|all> !denied_dst`. Squid evaluates one line left to right and stops at the first mismatch, so the `dst` lookup happens only after the port, the source and the category have matched. DESIGN §11.3's "by resolved IP" deny still applies to every allowed name. Every deny line ahead of the allows uses fast ACLs only (`port`, `method`, `dstdomain -n`, `dstdom_regex -n`, `myportname`, `src`).
  - `0.0.0.0/8` joins `always_denied.cidrs` (on Linux a connect to 0.0.0.0 reaches the proxy's own loopback). The renderer now refuses any `cidrs` entry that is not a literal network (`ipaddress.ip_network(strict=True)`).
  - `pinger_enable off` (the setuid ICMP helper already failed, since the container has no capabilities) and `visible_hostname ossbot-proxy` (no hostname/rDNS lookup at startup).
- **Alternative considered: an allowlist-only resolver for squid** (unbound/dnsmasq answering only allowlisted names). Rejected for v1. squid has one resolver for all listeners, and `web_public` (research, hermes) must resolve arbitrary names (DESIGN §11.3), so such a resolver would either cut `web_public` (a user-visible change) or need a second proxy instance just for `web_public` callers. The ACL order gives the same property for the confined callers, and the system test measures it: no query leaves the proxy for a name the caller may not reach. `web_public` callers can resolve anything by design, because they can already open a tunnel to anything.
- **Render tests** (`tests/unit/ctl/test_render.py`): every `dstdomain`/`dstdom_regex` has `-n`, and the only lookup ACL is `denied_dst` (`dst`). No deny line uses a lookup ACL. Every allow line is `port_* src cat_*|all !denied_dst`, and `deny ip_literal` precedes the first allow. The IP-literal patterns match 14 literal forms and none of 10 look-alike names. Both cases run with and without the hermes login window.
- **Probes** (`tests/system/test_egress_surface.sh`): a temporary raw-table chain counts the proxy's packets to its resolver that contain a fresh random label, plus every `in-addr.arpa`/`ip6.arpa` query. Per host port (3140 ossrunner, 3150 gatekeeper, 3128 host side) and per pool (fetch, llm, on test networks inside each /18), a random-label CONNECT and IPv4/IPv6-literal CONNECTs get 403, and the counters stay 0. Hermes's `web_public` lookup of its own random label is counted, as the control that the meter works. Against the round-3 config the same script fails (2 packets per denied label, 14 PTR packets). Doctor's "proxy denies" check also sends an IP-literal CONNECT through 3141.
- Offline reproduction with the pinned image (`--network none`, `hosts_file` mapping `203.0.113.10 api.github.com`): `dstdomain` gives 503 (tunnel attempted), `dstdomain -n` gives 403 `HIER_NONE`, and so does `-n` plus `deny ip_literal`.

## Implementation addendum (egress surface pass, 2026-10-18): IPv6 INPUT
The systematic pass behind P1-11/P1-12 (threat table in `docs/VERIFICATION.md`) found one more layer with no ossbot rule: ip6tables `INPUT`. Containers have no IPv6 address today (Docker disables IPv6 on interfaces of non-IPv6 networks, `ip6tables: false`), and no host service listens on a wildcard address. Still, a future host listener on `[::]` would have been reachable over a bridge's link-local address. `ossbot-firewall` (host part) now also renders ip6tables `OSSBOT-IN` (`-i docker0 -j DROP`, `-i br-+ -j DROP`) at position 1 of `INPUT`, which `--check` enforces. It is the IPv6 counterpart of the IPv4 `OSSBOT-IN` source drops.
## Implementation addendum (Phase 1 review P1-13, 2026-10-18): no Hyper-V sockets from ossbot units
Round 4 found a channel that no IP layer sees: `AF_VSOCK`. On WSL2 the guest reaches the Windows host (CID 2) over Hyper-V sockets. netfilter, the WSL NAT and the Hyper-V VM firewall filter only IP on the virtual NIC. Creating the socket needs no capability. As `hermes`, connects to CID 2 on ports 50000, 50002 and 50005 succeeded. The WSL source (`src/shared/inc/lxinitshared.h`) names them: 50000 is the init channel, 50002 the non-elevated drvfs Plan 9 server, 50005 crash-dump collection. 50002 answered a `9P2000.L` Tversion from `hermes` with Rversion. No attach was attempted. The ADR-0007 addendum covers what that server means.
- **Decision:** every non-root ossbot unit sets `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6`, so no `AF_VSOCK`, `AF_NETLINK` or `AF_PACKET`. Today these are `ossbot-gatekeeper` and `ossbot-sandboxd`, and the Phase 2 runner and hermes units must carry the same line. Neither service needs netlink: none of the code enumerates interfaces, and the proxy is an IP literal. glibc's `AI_ADDRCONFIG` falls back when netlink is refused. Checked live with the restriction in force: the gatekeeper's Telegram long-poll answers 200, and the sandboxd unit restarts, recovers and stays healthy through the round-4 bar. The Docker CLI (Go) talks to the filter socket from a transient unit with sandboxd's user and restriction (`docker ps` exit 0). Root units (filter, proxy launcher, watchdog, anchors, kill/resume) are not restricted. They are root, which owns the VM anyway (`mount -t drvfs` is a root operation).
- **Containers:** Docker's default seccomp profile refuses `socket(AF_VSOCK)` with EPERM. The filter pins `SecurityOpt == ["no-new-privileges"]` (no `seccomp=` override) and the runtime to runc. The proxy runs with the same options.
- **Not covered, by design:** sessions outside units (`runuser`, `wsl.exe -u <user>`) are unrestricted. They need root or the owner's Windows console, which ADR-0007 already treats as root-equivalent.
- **Tests:** `tests/unit/test_systemd_units.py` asserts the exact line for every `ossbot-*.service` with a non-root `User=`, so a Phase 2 unit without it fails the hermetic suite. `tests/system/test_egress_surface.sh` checks each loaded non-root unit's `RestrictAddressFamilies` and its MainPID's `Seccomp: 2`. It then runs a vsock connect in a `systemd-run` transient unit with the unit's user and restriction, which must get EAFNOSUPPORT (errno 97). The probe repeats in every sandbox pool, which must get EPERM. The proxy must show `Seccomp: 2` and no override. The control is an unrestricted `hermes` session, which must still reach 2:50002, so a refused probe is evidence.
- The same pass closed WSL's interop sockets to non-root uids (ADR-0007 addendum). It also added `198.18.0.0/15`, `192.0.0.0/24`, `224.0.0.0/4` and `240.0.0.0/4` to `always_denied.cidrs` (`198.18.0.0/15` is the fake-IP range of Windows VPN/proxy clients, reachable through the WSL NAT).
