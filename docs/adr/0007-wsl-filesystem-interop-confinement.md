# ADR-0007: Confine the ossbot distro to the repo folder, disable interop, unprivileged default user
Status: Accepted (revised in design rev 1) · Date: 2026-10-17 · Design: DESIGN.md §7.2, §7.6, §22.8

## Context
Hard user requirement: the distro may only see `D:\Work\autonomous-oss-contributor` and must not launch Windows executables. The VHD lives in `.wsl\ossbot` inside that folder. Review H7: a plain `wsl.exe` landing as `ossadmin` carried the operator API role.

## Decision
- `/etc/wsl.conf`: `[automount] enabled=false, mountFsTab=true`; `[interop] enabled=false, appendWindowsPath=false`; `[boot] systemd=true`; `[user] default=ossnobody` (no `ossapi`, `osscfg`, or `sudo`; egress rejected). Scripts always pass `-u root` or `-u ossadmin`.
- `/etc/fstab` managed block with one drvfs line: `D:\134Work\134autonomous-oss-contributor /mnt/d/Work/autonomous-oss-contributor drvfs metadata,uid=1000,gid=1500,umask=002 0 0`.
- Windows scripts stream every shell script over stdin (bootstrap, provision, secrets, kill, resume), so a broken mount never bricks provisioning; bootstrap verifies after `wsl --shutdown` and rolls back on failure.
- Distro autostart via a per-user Scheduled Task; idle shutdown disabled machine-wide (ADR-0013).

## Consequences
No `/mnt/c`, no Windows PATH, no `.exe` execution from Linux. Windows → Linux (`wsl.exe -d ossbot -u root`) still works for kill/resume, which also means Windows-user processes are root-equivalent over the distro (out of scope, ADR-0010). **Verify:** fstab escaping form, metadata/gid behaviour after Windows-side edits, `default=ossnobody` honoured.

## Implementation addendum (FEAT-004, 2026-10-18)
Verified live (DESIGN §23 items 3 and 4):
- The fstab source form `D:\134Work\134autonomous-oss-contributor` works on WSL 3.0.3: the repo is mounted as `9p` with `aname=drvfs;path=D:\Work\autonomous-oss-contributor;metadata;uid=1000;gid=1500;umask=002` and survives `wsl --shutdown`. The two fallback forms stay in `scripts/lib/wsl.sh`; bootstrap tries them only when the repo is not mounted at all (exit 3 of `wsl.sh check`).
- After `automount enabled=false` the ext4 directory `/mnt/c` left over from the old automount still exists; `wsl.sh apply` removes empty leftover drive directories through a bind mount of `/` after the restart, so `/mnt` holds only `d/Work/<repo>` (plus WSL's own `/mnt/wsl`, `/mnt/wslg`).
- Windows-side writes keep the group write bit: a file created from Windows shows `ossadmin:osscfg 775`; the gatekeeper (osscfg) can write `config/`, ossnobody and ossrunner cannot (`tests/system/test_config_write.sh`).
- **Deviation:** `[interop] enabled=false` alone does not unregister the `WSLInterop` binfmt_misc entry on 3.0.3 (it stays `enabled`, handler `/init`), so a PE file did not fail with ENOEXEC (the handler then failed on its vsock). `wsl.sh` installs `ossbot-nointerop.service` (sysinit, before the boot gate), which writes `-1` to every `/proc/sys/fs/binfmt_misc/WSLInterop*`. With it, executing `whoami.exe` from the mount fails with "Exec format error"; `wsl.sh check` and doctor fail if the entry reappears. Windows -> Linux `wsl.exe -d ossbot -u root --exec ...` keeps working.
- `[user] default=ossnobody` is honoured: plain `wsl.exe -d ossbot` lands as `ossnobody`; no Windows entries on PATH for ossnobody, ossadmin or root.
## Implementation addendum (Phase 1 review P1-13, 2026-10-18): the confinement holds against service uids, not root
The fstab drvfs line is not the only way to reach the Windows file system. It is mounted as `9p` with `trans=fd`, and init connects that fd over a Hyper-V socket to `wslservice.exe`'s Plan 9 server. In the WSL source, `LX_INIT_UTILITY_VM_PLAN9_DRVFS_PORT` is 50002 (non-elevated) and the admin port is 50003. The server runs as the Windows user. Live, as uid `hermes` before the fix, `AF_VSOCK` connect to CID 2 port 50002 succeeded, and a `9P2000.L` Tversion got an Rversion back. No attach was attempted. The server takes the path in the attach name (`aname=drvfs;path=D:\...`), so any process that can open that socket could ask for any Windows path the user can reach. `automount=false` and the single fstab line then confine nothing. The same holds for 50000 (init channel) and 50005 (crash-dump collection, which writes guest-supplied dumps on the Windows side).
- **Decision:** `AF_VSOCK` is refused to every non-root ossbot unit (`RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6`, ADR-0005 addendum) and to every container (Docker's default seccomp profile). Only root and the owner's own `wsl.exe` sessions keep it. They could also `mount -t drvfs` directly, which the Consequences above already accept (root-equivalent).
- **Interop sockets:** WSL also leaves `/run/WSL/<pid>_interop` (mode 0777, the binfmt handler's back end) in place. With `[interop] enabled=false` the host never answers it: a create-process request through it as `hermes` timed out (`UtilAcceptVsock: accept4 failed 110`), and a `cmd.exe /c echo` probe wrote nothing. `ossbot-nointerop.service` now also sets `/run/WSL` to 0700, so no non-root uid can connect at all. `wsl.sh check` and doctor (`interop sockets`) fail if the mode drifts. `test_egress_surface.sh` refuses the connect for all five service uids. New `wsl.exe` sessions keep working (their per-session socket is created by root init).
- `/mnt/wsl` (a 1777 tmpfs shared by all distros in the VM) stays a cross-distro channel only. WSL on this machine runs only ossbot (ADR-0013), and the tmpfs does not reach the Windows host. WSLg is off (`guiApplications=false`), so `/mnt/wslg` has no X11, Wayland or PulseAudio sockets that could reach the host's RDP client or clipboard.
