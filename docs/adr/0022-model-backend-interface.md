# ADR-0022: Model backend interface: pluggable model backends inside the unchanged sandbox, probe and key-scan boundary
Status: Accepted (2026-10-20, post-v1 Package BACKEND) · Design: DESIGN.md §15, §16, §10.6, §10.9, §8.3 · Related: ADR-0002 (Hermes + kiro-acp), ADR-0005 (sandbox and egress), ADR-0009 (global model switch), ADR-0011 (Kiro CLI), ADR-0017 (key-holding containers), ADR-0018 (Hermes tool surface)

## Context
The owner expects contributors to add other model backends later (Claude Code, Codex, OpenAI-compatible APIs) and wants the code modular, "especially from the Kiro ACP perspective", while the foundations stay where they are. Before this ADR both model paths were Kiro-only and their seams were implicit:
- **Pipeline roles (Kiro headless).** `runner.llm.Kiro` resolved the role's model from `config/models.yaml` against the gatekeeper catalog, wrote the prompt and inputs, and submitted a sandboxd job `{entrypoint: "kiro", profile: ROLE_PROFILE[role], args: {role, prompt_file, model, effort}}`; the answer came from `<role>.events.jsonl` through `runner.output_parse`. sandboxd admitted the job only after `KiroArgs` and catalog validation and the probe gate for the exact tuple (`sandboxd.probes.compute_key`: CLI, images, agent config, settings, trust mode); `sandboxd.argv` passed `KIRO_API_KEY` by name only for the key pairs `(research, kiro)`, `(agent-llm, kiro)`, `(catalog, list_models)`, and the root Docker filter (`dockerfilter.rules.KEY_PAIRS`) enforced the same pairs. The image entrypoints `sandbox/entrypoints/kiro.sh` and `list_models.sh` ran `kiro-cli chat` headless with `TRUST_TOOLS` and the agent `.kiro/agents/ossbot-<role>.json`.
- **Catalog.** The `list_models` job → `common.models.parse_list_models` → the gatekeeper catalog → `sandboxd.models.CatalogCache`.
- **Safety probes.** `sandboxd.probes.PROBES` (`research_deny`, `symlink`, `coder_surface`, `settings`, `workspace`), run by `jobs.ProbeRunner.run_all`; prompts in `sandbox/probes/*.md`.
- **Key-scan.** `sandboxd.keyscan.KeyScanner` looks for exact credential values and their encodings in every output and log; `sandboxd.main` built it from `KIRO_API_KEY` and `GITHUB_READ_TOKEN`. The `ksk_` format regex lived in `ctl.doctor.FORMATS`.
- **Assistant (Kiro V3 ACP).** Hermes v0.22.2 loads the provider plugin `kiro-acp` from `vendor/hermes-kiro-provider` (`kiro_acp/v3.py`, an OpenAI-client facade over `kiro_acp/v3_core.py`, the ACP transport); `hermes/config/config.yaml.j2` sets `model.provider: kiro-acp`; the per-turn model comes from `config/models.yaml` (`ModelsSource`, roles chat/vision/test); the root probe is `ctl/hermes_probe.py` (it loads the root-owned `v3_core.py` by path and checks the tool surface, denials and exfiltration); the gatekeeper relays turns through `gatekeeper/chat/backend.py HermesApiBackend`. Nothing in the pipeline calls Hermes.

## Decision
### Two small layers
1. **`ossbot.common.backends`** (pure data, no component imports, mypy strict, covered by the "common depends on no component" contract). A frozen `BackendSpec` per backend: `name`; `kind` (`pipeline` = headless role jobs in sandboxd, `assistant` = a Hermes provider plugin); `sandbox_entrypoint` and `catalog_entrypoint`; `key_profiles` (the sandboxd profiles whose role job gets the credential; with the catalog entrypoint they give `key_pairs()`); `credential_env` (env names whose values sandboxd key-scans); `credential_patterns` (format regexes for doctor and setup); `required_probes`; `hermes_provider`. Registry `BACKENDS = {"kiro": KIRO_HEADLESS, "kiro-acp": KIRO_ACP}`, `backend_for(cfg)`, `pipeline_credential_env()`.
2. **`ossbot.runner.backends`**: `base.ModelBackend`, a `runtime_checkable` Protocol with `run_role(cid, role, out_model, text, files, *, timeout_s, schema_hint, check) -> LlmResult` (a validated answer, or `StageFailed`/`Interrupted`), `resolve(role)`, `list_models()` (the gatekeeper catalog rows the backend resolves against) and `probe_surface() -> BackendSpec`. `kiro_headless.KiroHeadlessBackend` is the former `runner.llm.Kiro`, moved without a logic change (`run_role` is `invoke`); `runner.llm` keeps `Kiro`, `ROLE_PROFILE`, `LlmResult`, `StageFailed`, `as_prompt` and `new_run_id` as re-exports. `select_backend(cfg)` maps the configured name to its implementation and raises `UnknownBackend` for anything else; `StageContext.kiro()` selects at every role call from the live `models.yaml` (the same live read as model resolution; an unreadable file with no last good copy keeps the default, which then fails the stage with `model_unavailable` as before).

### Config
`config/models.yaml` accepts a top-level `backend` (schema `ModelsConfig.backend: Literal["kiro"] = "kiro"`). Omitted means `kiro`, today's behaviour; any other value fails validation like any other invalid `models.yaml` (the runner keeps the last good version and alerts, the writer returns 400). The shipped file sets `backend: kiro` (uncommented once the code that accepts the key was deployed; until then it was a commented line, because the older deployed schema would have refused it); the gatekeeper writer (ruamel round-trip) keeps the key. One wire change: the gatekeeper's `GET /v1/models` returns `ModelsConfig.model_dump()`, which now includes `"backend": "kiro"`; its only consumer, `ossctl model list`, validates the body with the same `ModelsConfig`, so nothing reads it differently. The assistant backend is fixed (`ASSISTANT_BACKEND = "kiro-acp"`, named by the Hermes config); there is no config key for it. The vendored `ModelsSource` reads only `default`, `roles` and `fallbacks` and ignores other keys.

### Key-scan, probes and filter bound to the spec
- sandboxd scans for (and its log redactor removes) the values of `pipeline_credential_env()` (every registered pipeline backend; kiro: `KIRO_API_KEY`) plus `GITHUB_READ_TOKEN` (`sandboxd.main.scan_secrets`). Today that is the same two values. `KeyScanner` and its needles are unchanged. `credential_patterns` are not added to the output scan, because that would redact more than today; they are the hook for a future backend whose key format is known.
- `sandboxd.probes.PROBES` stays the single probe list and `compute_key` is unchanged. Every pipeline spec's `required_probes` equals `PROBES` (unit test).
- The root Docker filter is unchanged. Every pipeline spec's `key_pairs()` must be a subset of `dockerfilter.rules.KEY_PAIRS` and `sandboxd.argv.KEY_PAIRS`, and its `credential_env` names must pass the filter's env check for exactly those pairs and be refused for repo-code profiles (unit test). A new backend therefore needs a reviewed filter change, which is intended.
- Import-linter: "Model backends never import the gatekeeper, sandboxd or the Docker filter" (`ossbot.runner.backends` → forbidden `ossbot.gatekeeper`, `ossbot.sandboxd`, `ossbot.dockerfilter`, `ossbot.ctl`); the existing "untrusted-side components never import the gatekeeper" and writer contracts still cover `ossbot.runner`.

### What does not move
The gatekeeper (approvals, the two two-tap gates bound to content and mode, the state machine and its actor table, `submit.py` → `github_writer.py` as the only GitHub write path, the review mirror), dry-run and kill/pause/lifecycle, the sandbox profiles and their mounts, the egress allowlists and squid, the Docker filter rules, the probe list, the probe gate key and the probe prompts, the key-scan concept and needles, the commit identity rules and every invariant I1-I13. No backend gets a write token, an approval path, a host mount or a route around the probe gate.

### Rules every new backend must meet
- **Official CLI or API only.** A backend uses the provider's official CLI or public API under the user's own account and terms. Never a ToS-violating proxy, a MITM model router (ADR-0002 rejected 9router and OmniRoute for this reason), a reused desktop session or a scraped web endpoint, and never another product's credentials.
- **Inside the existing boundary.** A pipeline backend runs only as a sandboxd job in the existing profiles (`research`, `agent-llm` for the coder's model side, `catalog` for its model list), chosen by `ROLE_PROFILE`, never by the backend. Repo code still runs only in credential-free containers (I5).
- **Probes.** It passes all of `PROBES` (`research_deny`, `symlink`, `coder_surface`, `settings`, `workspace`) for its exact CLI/image/agent-config/settings/trust-mode tuple before any job runs; its image entrypoint feeds the same probe prompts.
- **Credentials.** It declares `credential_env` (key-scanned in every output, bundle and log) and `credential_patterns`; its key lives in `sandboxd.env` only, is passed by name only, and gets a documented optional entry in `scripts/setup-secrets.ps1`.
- **Filter and egress.** A reviewed change to the Docker filter's `KEY_PAIRS` and env-name check (root TCB), the matching `sandboxd.argv` pairs, and an egress category in `config/egress.yaml` added to the `research`, `agent-llm` and `catalog` profiles only (never `fetch` or `validate`).
- **Models.** Its model ids live only in `config/models.yaml` (`tests/unit/test_no_hardcoded_models.py`); a catalog entrypoint whose output parses into `CatalogEntry`; the `ModelsConfig.backend` literal and `IMPLEMENTATIONS` gain the name in the same change.
- **Tests.** `tests/unit/common/test_backends.py`, `tests/unit/runner/test_backends.py` (interface conformance, selection, a job-spec snapshot), `tests/unit/sandboxd/test_backend_surface.py` (probes, key pairs, filter, scan list), `tests/unit/gatekeeper/test_models_admin_backend.py`, the existing sandboxd/dockerfilter suites unchanged, the hermetic suite (`pytest -m "unit or telegram or acp or e2e"`), and live: `ossctl doctor --probes` PASS and `ossctl kiro smoke`-style round-trip on `roles.test`.

### Assistant backends (Hermes provider plugins)
Hermes reaches models only through a provider plugin; that is the path for other assistant providers. A new one needs: a Hermes `model-provider` plugin (a directory with `plugin.yaml` `kind: model-provider` and the provider module, vendored under `vendor/` with its upstream commit and license, installed into `/home/hermes/.hermes/plugins/model-providers/<name>` by provisioning); `model.provider: <name>` in `hermes/config/config.yaml.j2`; per-turn models from `config/models.yaml` roles `chat`, `vision` and `test`; the tool surface allowlist of ADR-0018 (only `web_search` and `web_fetch`, everything else refused); a `BackendSpec` of kind `assistant` with `hermes_provider`, `credential_env` (in `hermes.env`, readable by uid `hermes` only) and `credential_patterns`; a root probe like `ctl/hermes_probe.py` (the root-owned copy of the transport loaded by path, the tool surface, deny and exfiltration checks, the result file the gatekeeper reads) whose failure closes the relay; egress through the `hermes` host caller only; and the `tests/acp` suite against a scripted fake of the provider's protocol. The gatekeeper relay (`HermesApiBackend`) and the approval path are untouched.

## Consequences
- Behaviour today is identical: the same job specs (a byte-equal snapshot test of the moved code), the same probes, the same two scanned values, the same filter, the same Hermes provider. Existing tests changed only in imports (none needed changing).
- Adding a backend is a reviewed, multi-file change by design: the spec, an implementation, an image entrypoint, a filter and egress change, setup-secrets, probes passing live. It cannot be switched on from Telegram (`/model` writes roles only) and an unregistered name in `models.yaml` never validates.
- No Claude, Codex or OpenAI backend is implemented here; CONTRIBUTING "Adding a model backend" is derived from this ADR.

## Implementation addendum (post-v1, 2026-10-22): `OutputInvalidFailed.last_text`

- **Cause** (`.agents/tasks/stuck-after-gate1-2026-10-17.md`, root causes 2 and 3): a planner answer that judged the item `feasible: false` broke the `Plan` schema twice on one overlong `approach` line, so the item became FAILED `output_invalid` and the verdict was lost.
- **Contract change**: an answer still invalid after the one repair retry raises `runner.errors.OutputInvalidFailed`, a `StageFailed` subclass (`error_class` `output_invalid`) whose `last_text` is the last answer's assistant text (untrusted, capped by `output_parse.MAX_TEXT`). Every backend's `run_role` must raise it for that case (`base.ModelBackend` docstring). Every `except StageFailed`, `StageRun.__exit__` and the scheduler treat it as before.
- **Its one reader**: `runner/stages/plan.py salvage_infeasible` validates only `feasible` (`StrictBool`) and `summary` of the last fenced JSON through `outputs.InfeasibleVerdict` (`extra=forbid`); a strict `false` abandons `plan_infeasible` (`schema_salvaged: true`), anything else re-raises. It can only stop work, so the backend boundary, probes, key scan and approval path are unchanged (I8, I9; DESIGN §9.7).
