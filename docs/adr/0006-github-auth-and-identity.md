# ADR-0006: GitHub auth, fork-and-PR flow, and commit identity
Status: Accepted (revised in design rev 1) · Date: 2026-10-17 · Design: DESIGN.md §2, §9.11, §12.4-12.6, §18.3

## Context
GitHub documents that fine-grained PATs cannot contribute to public repos where the user is not a member. The work account `@<work-login>` must never be used. User decision (2026-10-17): every upstream commit uses author == committer == `Signed-off-by` == `Amsal Khan <md.amsalkhan@gmail.com>`; the GitHub login stays `Amsal1`. DCO checkers compare the sign-off with the author, so these are separate concepts from the API identity.

## Decision
- Identity fields in the gitignored `config/profile.yaml` (ADR-0015): `github_login` (owner: `Amsal1`), `commit_name` (`Amsal Khan`), `commit_email` (`md.amsalkhan@gmail.com`), `signoff: true`, `forbidden_logins` (`<work-login>`, kept in a monotonic DB floor). Loaded only through the config snapshot.
- Write: classic PAT on `Amsal1` with only `public_repo` (no `workflow`; workflow edits are forbidden by a hard-coded floor), held only by the gatekeeper and used only through proxy port 3150.
- Read: fine-grained PAT on `Amsal1`, "Public repositories (read-only)", held by the runner. Sandboxes clone anonymously.
- Commits are created by the deterministic package job in a fresh repo with the identity above and `Signed-off-by: Amsal Khan <md.amsalkhan@gmail.com>`. The gatekeeper verifies author == committer == last sign-off == identity, single commit on an upstream base, before showing anything.
- Flow: reuse an `Amsal1` fork whose parent is the upstream (langfuse and n8n forks exist), else create one; push the approved SHA to `ossbot/<issue>-<slug>-<cid6>`; open the PR with `maintainer_can_modify: true`. Token login must equal `Amsal1` before any write; `<work-login>` triggers kill.
- This harness repo uses repo-local git config with the same name/email and normal commits (no `GIT_AUTHOR_*`/`GIT_COMMITTER_*` overrides). A future private remote for it uses a separate credential, never the gatekeeper PAT.
- Repos requiring signed commits are skipped in v1. (Superseded by the 2026-10-21 addendum below: skipped only without the optional SSH signing key.)

## Consequences
Classic PAT is broad across Amsal1's public repos; mitigated by the gatekeeper being the only holder, proxy-limited egress, and policy. **Verify:** `md.amsalkhan@gmail.com` is verified on `Amsal1` and not linked to `<work-login>`; `X-OAuth-Scopes`; fine-grained PAT limitation still current.

## Implementation addendum (FEAT-002, 2026-10-17)
- Checked on docs.github.com (REST `repos/forks`): `POST /repos/{owner}/{repo}/forks` accepts body `name` (new name for the fork) and `default_branch_only`, answers 202 and forks asynchronously (wait up to 5 minutes). The gatekeeper sends `{name, default_branch_only: true}` and polls `GET /repos/<login>/<name>` every 3 s for up to 5 min. Docs now show `X-GitHub-Api-Version: 2026-03-10`; the gatekeeper pins `2022-11-28`, which stays supported for at least 24 months after its successor (re-check in FEAT-008).
- Gatekeeper reads (identity, live checks, reconciliation) and writes use the write token through proxy 3150 (`github_read.make_client`); only `gatekeeper.submit` can reach the write calls (import-linter, `unmatched_ignore_imports_alerting = error`).
- `GET /user` login and `X-OAuth-Scopes` (`public_repo` or `repo`) and the live fork/push/PR behaviour remain **pending live probe (needs GITHUB_WRITE_TOKEN)**; until then every submit is refused with `no_write_token` (PLAN Decision 5).

## Implementation addendum (FEAT-006 review round 2, 2026-10-18): DESIGN §23 items 17 and 18, read-only part
- Item 17, read-only part. The write token now exists. `ossctl doctor` (full) sends `GET /user` with it and checks the login and `X-OAuth-Scopes`: `public_repo` is present and `repo`, `workflow` and `admin:*` are absent (the result is in VERIFICATION "Phase 2 live checks"). Per the GitHub docs, `public_repo` limits a classic token to public repositories ([scopes for OAuth apps](https://docs.github.com/apps/building-oauth-apps/understanding-scopes-for-oauth-apps)), and scopes never add permissions beyond the user's own. Forking, pushing to the fork, opening a PR and commenting are all writes to public repositories.
- Item 17, write part (sufficiency in practice, fork creation latency, secondary rate limits) stays pending. It needs a live write, and the build makes none (hard rule 2). It is checked at the first owner-approved submit after the owner turns dry-run off, and recorded by FEAT-011 under "User action needed" (TRACEABILITY DES-V-17).
- Item 18 (the commit email is verified on `Amsal1` and not linked to `<work-login>`) cannot be read with either token, because GitHub's email endpoints need the `user:email` scope, which neither token has. It also has no product check yet. GitHub attributes a commit to the one account on which its email is verified, so the first PR's commit attribution answers it, as does the owner's Settings → Emails page. Pending, FEAT-011 "User action needed" (TRACEABILITY DES-V-18).

## Implementation addendum (owner addition 2026-10-21): SSH commit signing

Context: grafana/loki's CONTRIBUTING says Grafana Labs repositories will require signed commits and that unsigned commits and PRs (agent-authored ones included) are rejected and closed. The DCO `Signed-off-by` trailer is not a signature, and the old vet regex missed that verb-first wording.

- **Detection.** `runner/stages/vet.py SIGNED_RE` now also matches "require(s/d) signed commits", "require all commits to be signed", "signed commits are required/mandatory", "unsigned commits … rejected/closed/not accepted", "commit signature verification", "commits … must be (GPG/SSH-)signed" and "GPG/SSH-signed commits". DCO wording ("Signed-off-by", "signed off") and CLA wording are excluded (tests use the Loki sentences verbatim).
- **Signing.** The gatekeeper SSH-signs the packaged commit (DESIGN §12.5b). The optional `GITHUB_COMMIT_SIGNING_KEY` (OpenSSH ed25519, no passphrase) is entered with `setup-secrets.ps1` as a key-file path, streamed in the NUL-separated record (multi-line values are fine there), checked with `ssh-keygen -y -P ''` and stored in `gatekeeper.env` only as the one-line body of the block. The signed commit is made in the mirror from the verified one (identical tree, parent, author, committer, message; `gpgsig` inserted where git puts it), checked with `git verify-commit`, and becomes the packaged SHA: preview, binding (I1, I12) and push use it, I6 is checked on both. Every rev packaged after the key is set is signed, including Request-changes and fix-round revs. Fix rounds take the signed head from `GET /v1/contributions/{cid}/head-bundle`.
- **Policy.** `policy.commit.signing: auto | required | off` (default `auto`: sign when the key is set). Vet skips `signed_commits_required` only when `GET /v1/signing` says nothing will be signed. Approve, the Confirm preflight and submit refuse an unsigned rev for a repo vet flagged `signed_commits_required`. Cards and the explorer say "🔏 Commit signed (SSH, key SHA256:…)" or "⚠️ Commit not signed".
- **Key handling.** `ssh-keygen` reads the key from an inherited 0600 memfd (`/proc/self/fd/N`), never a file, argv or the environment; the gatekeeper's U14 scanner and log redactor hold its 70-column lines (the whole body is longer than the scanner's 256-character value limit); sandboxd's key scan has no needle for it because the key never reaches sandboxd. Only the public fingerprint is logged or shown.
- **Doctor.** `ossctl doctor` signs and verifies a throw-away commit with the key and (full mode) checks that its public half is among the login's SSH signing keys.
- **Verified (2026-10-22).** `GET /users/{username}/ssh_signing_keys` lists a user's signing keys without authentication, `per_page` up to 100 ([REST: SSH signing keys](https://docs.github.com/en/rest/users/ssh-signing-keys)); GitHub verifies SSH commit signatures for keys added with key type "Signing Key" ([commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification)). Live probes in the distro: git 2.43.0 and OpenSSH 9.6p1; `ssh-keygen -Y sign -n git -f /proc/self/fd/N` signs stdin with a memfd key (mode 0600); `git verify-commit` with `gpg.format=ssh` accepts the inserted `gpgsig` (tests/unit/gatekeeper/test_signing.py). GitHub shows "Verified" only when the committer email is a verified email of the account (ADR item 18 above).
- **Open.** Issues skipped earlier as `signed_commits_required` stay never-retry (`common/rediscover.py`); new issues of such a repo are allowed once the key is set. The live grafana/loki contribution packaged unsigned before this change is not touched: the owner adds the key, then taps Request changes, and the next rev is signed.

## Implementation addendum (2026-10-23): package job stages the work tree in place

Context: c_D1CYR0EKGR (koala73/worldmonitor#8598) failed at package #1 with `exit_11`. The fetch had installed about 658 MB of npm downloads into `/work/repo` (an ignored `node_modules`). `package.sh` copied the whole work tree, ignored files included, into the package container's `/tmp` (tmpfs, 2 GiB, the Docker filter's `TMPFS_MAX`) with `rsync -a --delete --exclude=/.git` only to `git add -A` it there. rsync hit ENOSPC on `node_modules/pdfjs-dist/...` and exited 11 ("error in file I/O"); `set -e` ended the script before `result.json`, so sandboxd reported `exit_<code>` and the owner's FYI had no reason. Latent since v1; not a regression (signing, scout and discovery changes never reach the package job).

- **Decision.** No copy. After the objects-only fetch, `symbolic-ref HEAD refs/heads/ossbot-change`, `update-ref refs/heads/ossbot-change ROUND_BASE` and `read-tree ROUND_BASE` put the base in the fresh repository's branch and index without writing a tracked file to `/tmp`. Then `git --git-dir=/tmp/pkg/.git --work-tree=/work/repo add -A` and the commit run against the work tree in place. Bundle, patch and numstat are unchanged. A bigger tmpfs was ruled out (it weakens a filter rule and only moves the limit), and so was an rsync `.gitignore` filter (not git's semantics; with `--delete` it drops force-tracked ignored files).
- **I6 unchanged.** Still a fresh repository with the fixed identity, dates and `Signed-off-by` trailer, the hardened `-c core.hooksPath=/dev/null -c core.fsmonitor=false -c protocol.file.allow=never` flags and no system or global config. `--git-dir` is explicit, so `/work/repo/.git` (config, hooks, `info/attributes`, `info/exclude`) is never read; the work tree's own `.gitignore`/`.gitattributes` apply exactly as they did to the copy. `read-tree` leaves no stat data, so `add -A` re-hashes every tracked path. The gatekeeper's re-verification (§12.5) and SSH signing are untouched.
- **Probe (2026-10-23, distro git 2.43.0).** A throwaway comparison of the old procedure (checkout, rsync copy, `add -A`) and the new one on a `--depth 1` clone with an edit, a deletion, a new file, an exec-bit change, a symlink, a force-tracked ignored file and an ignored `node_modules` gave the identical tree SHA, parent = base, the given identities and the trailer; `/work/repo` was not modified. `tests/unit/entrypoints/test_package_script.py` keeps that comparison and adds hostile repo config, hooks and filters that must never run.
- **Named failures.** Each remaining step has its own error class in `result.json` (`base_missing`, `empty_change`, `stage_failed`, `commit_failed`, `bundle_failed`, `patch_failed`, `diffstat_failed`), with an `ERR` trap backstop (`package_failed`); all exit 3. The runner (`runner/stages/package.py PACKAGE_FAILURES`) turns a failed package job into a fixed owner sentence in the FAILED evidence `summary`, shown as the terminal FYI's "Why" line; an unnamed class (`exit_N`) names the job's run id and its redacted log path. `/logs` still can't show sandbox job logs (a permission change, left for its own review).
