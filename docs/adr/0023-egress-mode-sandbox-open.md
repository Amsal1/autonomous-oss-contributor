# ADR-0023: Egress mode `sandbox_open`: repo code may reach the public web, guarded per job (amends I5)
Status: Accepted (owner decision 2026-10-21; built in post-v1 open discovery FEAT-004/FEAT-005, 2026-10-22) · Design: DESIGN.md §10, §10.3, §11, §11.5, §13; open-discovery design §12, §13 · Amends: ADR-0005 (I5) · Related: ADR-0012 (stack pool), ADR-0016 (retention)
Amended by ADR-0025 (2026-10-24): a fifth mode `sandbox_full` with the same squid rules; any floor attempt now holds in every mode (reason `egress_floor`), the volume guard of this ADR stays a hold in `sandbox_open` and becomes a note for web jobs of `sandbox_full`; proxy-unaware tools reach squid through the in-sandbox netshim; the owner's public address is a floor.

## Context
Open discovery proposes work on any popular DevOps/platform repository, not only the seed list. Many of them fetch their dependencies from hosts no category of `config/egress.yaml` lists (Go module proxies of a vendor, a project's own artifact host, Helm repositories, cloud SDK mirrors). Until now the rule was absolute: `fetch` and `validate` (the only profiles that run repo code) never get `web_public`, so such a repo either fails its fetch or is skipped by the egress precheck (rule 14). The owner decided on 2026-10-21 that repo code may reach the public web in a fourth, explicitly chosen egress mode, provided every network floor stays and a per-job guard stops a job that behaves like exfiltration, pausing only that contribution.

## Decision
- **A fourth mode `sandbox_open`** (`allowlist` < `research` < `open` < `sandbox_open`): everything `open` grants, plus `web_public` for `fetch` and `validate`. The schema admits a `fetch`/`validate` grant only in `sandbox_open`, only `web_public`, and the same list for both (they share the fetch squid pool). The renderer asserts the rest: `pool_fetch` gets `all` only in `sandbox_open`, the llm pool only in `open`/`sandbox_open`, runner and gatekeeper never; the always-denied CIDRs and names (`!denied_dst` on every allow line, the denies ahead of every `all` allow), IP-literal denies and the DNS controls are identical in all four modes.
- **Shipped, not default (owner answer O7).** `egress.mode_default` stays `open`; the owner switches with `/egress sandbox_open` (two-tap, audited) or `ossctl egress mode sandbox_open` (TTY confirm). A redeploy changes no live mode. Flipping the default is backlog B6.
- **I5 text change.** I5 used to say egress "only through the proxy with a per-profile allowlist". It now reads: egress only through the proxy; per-profile category lists, except that in egress mode `sandbox_open` `fetch`/`validate` also get `web_public` behind the always-denied floors and the per-job anomaly guard; repos marked `egress: strict` keep the base list in every mode. The credential half of I5 is absolute and unchanged: no container both holds a credential and runs repo code; key-holding containers never mount an attacker-writable path; no host mounts or sockets.
- **Per-repo strict override.** `egress: strict` on a `targets.yaml` entry or in `targets.defaults`, or `discovered_targets.egress_strict` (`ossctl targets strict`), makes the repo's fetch/validate jobs run on the `fetch-strict`/`validate-strict` network profile, whose squid pool `pool_strict` is rendered from the fetch base list in every mode.
- **The /18 split.** The last /18 of the task range is split: `pool_strict` = `10.213.192.0/19`; `10.213.224.0/19` stays reserved for the Phase-2 stack pool (ADR-0012). No rendered pool overlaps another (renderer test). The strict system-test probe uses `10.213.223.240/28`; `test_proxy_dns.sh` keeps `10.213.255.240/28` in the unused stack half.
- **Fail closed on the strict decision.** Every fetch/validate `JobSpec` must carry `egress: mode | strict`; sandboxd answers 400 `egress_required` without it and 400 `egress_not_applicable` on any other profile; the runner raises `StageFailed("egress_required")` before submitting, and every call site passes `target(sc, upstream).egress`.
- **The guard (open-discovery design §13).** squid logs `logformat ossbot %ts.%03tu %>a %>lp %Ss/%03>Hs %rm %ru %<a %>st %<st %tr` (named-option form `access_log stdio:… logformat=ossbot rotate=0`; the positional form makes squid 6 read `rotate=0` as an ACL name, ADR-0005 FEAT-004 addendum). sandboxd's `EgressMeter` attributes lines to a fetch/validate job by its /28, listener port 3128 and start time, counts distinct hosts (denied ones too), bytes up and down. A job over `egress.anomaly` (`max_hosts` 60, `max_upload_mb` 50, `max_download_mb` 6144; config-only, never Telegram-tunable) is stopped (`egress_anomaly`, staging discarded) and the gatekeeper is asked for a **contribution hold**: only that contribution's stages, `/package` and submit writes stop; the owner gets a P1 card and resumes with a two-tap (or `ossctl egress release`). If the hold call fails with a 5xx or a transport error, sandboxd keeps the cid blocked locally (423 `egress_anomaly_pending`) and retries every 30 s; a 4xx answer (400 `schema_error`, 404 `unknown_cid`) is final: the row keeps `rejected_code`, an ERROR is logged and only the owner's release clears it (review-3 M3). Strict jobs are metered too. Every job's summary goes to `/srv/ossbot/logs/runs/<run_id>.egress.json`.
- **Retention.** `ossbot-proxy-rotate` (daily 00:10 UTC) renames `access.log` and signals `squid -k rotate`; `ossctl gc` deletes rotated logs after `retention.proxy_logs_days` (≥ 30) and old summaries with the run logs.

## Verified facts (web-research rule)
- V10 squid logformat codes, https://www.squid-cache.org/Doc/config/logformat/ (read 2026-10-21): `%>a` client source IP, `%>lp` local listening port, `%ts` seconds since epoch, `%tr` response time (ms), `%>st` total size of the request received from the client, `%<st` total size of the reply sent to the client, `%<a` server IP. That a CONNECT line carries the tunnel's byte totals and is written when the tunnel closes is not taken from the docs text: `tests/system/test_proxy_log_bytes.sh` checks it on the live proxy (close-out).
- V11 rotation, https://www.squid-cache.org/Doc/config/logfile_rotate/ and https://www.squid-cache.org/Doc/config/access_log/ (read 2026-10-21; the named-option form re-read 2026-10-22 with https://raw.githubusercontent.com/squid-cache/squid/v6/src/cache_cf.cc and https://raw.githubusercontent.com/squid-cache/squid/v6/src/log/FormattedLog.cc): with rotation 0 squid closes and reopens its logs on `-k rotate` and the operator renames them first; from squid 4 stdio access logs take the `rotate=N` option; use `squid -k rotate` rather than `kill -USR1`. Pinned squid stays `6.14-0ubuntu0.24.04.4`; `pid_filename /run/squid.pid` (tmpfs in the container) is what `-k rotate` reads.
- **V10 fallback (stop and ask).** If `test_proxy_log_bytes.sh` shows a CONNECT line without the tunnel's totals (`%>st` 0 for an upload, `%<st` below the downloaded size), the byte limits would be blind: the implementer stops and asks the owner before `sandbox_open` is offered, and the run report says "do not switch to sandbox_open". No hosts-only guard is shipped in place of byte metering. Because `mode_default` stays `open`, nothing is widened meanwhile.

## Alternatives
- Promote each uncategorised host into `egress.yaml` by hand (the status quo): safe but it blocks most of open discovery's repos until the owner edits config.
- TLS interception to see paths and bodies: rejected again (ADR-0005), CA distribution and complexity.
- A global pause on an anomaly: rejected; the owner asked that only the affected contribution stops.
- A hosts-only guard when byte totals are not available: rejected as the V10 fallback (it misses the upload signal the owner named).

## Consequences and residual risks
- HTTPS content, paths and query strings inside a tunnel are invisible; only host, port, bytes, timing and the result are logged.
- A slow leak under the thresholds is not detected; one long tunnel is invisible until it closes (the job timeout bounds it and the `finish` check always runs).
- Third-party abuse from the owner's IP (scanning, spam through public endpoints) is bounded only by the limits, the job timeout and the always-denied floors.
- DNS-label exfiltration through denied names shows up in the host count (denied requests count), not as a separate signal.
- `research` and `agent-llm` jobs (key-holding, no repo code) are not metered (backlog B5); a request-rate threshold is backlog too.
- `max_consecutive_stage_failures` (policy.yaml `anomaly`) is unrelated and not enforced today; a hold never counts as a stage failure.
