# ADR-0003: A deterministic gatekeeper is the only GitHub write-token holder and policy core
Status: Accepted (amended in design rev 5 on 2026-10-18; revised in design rev 1, rev 3 and rev 4) · Date: 2026-10-17 · Design: DESIGN.md §8, §9.2, §9.4, §12

## Context
LLM sessions read hostile text (issues, comments, repo files, web pages). If any LLM-adjacent process can perform GitHub writes or decide approvals, prompt injection can publish under `Amsal1`.

## Decision
A small Python service (`ossbot-gatekeeper`, Unix user `gatekeeper`) is the trusted computing base together with the root helpers (dockerfilter, enforcer, watchdog):
- only non-root user that can read the classic PAT; the only module calling write APIs is `gatekeeper/submit.py` (import-linter enforced);
- owns control state (kill/pause/dry-run, dry-run default ON), the config snapshot, the contribution state machine with **actor-owned edges** (worker / gatekeeper_internal / human; approval and submit edges are never worker edges), approvals, rate limits, policy checks, and the hash-chained audit log;
- derives every artifact the human reviews from its own per-contribution mirror (ADR-0014);
- exposes a Unix-socket API with roles from `SO_PEERCRED` (operator, worker, sandbox, requester). There is no approve endpoint; approval exists only as a Telegram two-tap flow.
- Asymmetric control: any role may request stop; only the human may request go. Every local operator go action is announced on Telegram.

## Revision 3 amendments (design review round 3, M4/M5/M6)
- M4: the state machine owns "an open PR is never orphaned". While `pr_number` is set, every requested move to `FAILED` or `ABANDONED` is redirected to `WATCHING` (`fix_round_failed:<class>`) and the task volume is kept. The only terminal exits are `MERGED`/`CLOSED` (worker, observed on GitHub) and `ABANDONED` through the human "Stop watching" button. `branch_moved` disables further automated fixes for that PR.
- M5: submission is checkpointed against kill and pause before each write. An interrupted submission ends `SUBMIT_FAILED` and needs a fresh approval. `executing` actions are reconciled at start by reads only, and writes are never resumed automatically.
- M6: one non-terminal contribution per issue, enforced by a partial unique index. Re-discovery is decided by deterministic rules in the gatekeeper's insert path: never after reject, merge or close; after a dry run only once dry-run is off; after failure or expiry only after a 7-day cooldown; after a repo-policy skip only once the human unlocks the repo.

## Revision 4 amendments (design review round 4, R4-N2/R4-N3)
- R4-N2: each submission checkpoint requires `running` and also `control_state.dry_run == snapshot.dry_run`. A dry-run toggle that lands mid-submission stops the next write, the same way a pause does: `interrupted`, `SUBMIT_FAILED`, "mode changed during submission", and a fresh approval is needed.
- R4-N3: the closed API gains `POST /v1/models/catalog` (worker) for the runner's catalog upsert. It takes 1-200 entries, validates ids with the `--force` regex, has no `forced` field, and never changes `forced`.

## Alternatives
- Let Hermes hold the token with "careful prompts": rejected (prompting is not a control).
- Runner and gatekeeper in one process: rejected (runner parses large untrusted LLM output; keep the TCB small).

## Consequences
More moving parts (runner ↔ gatekeeper API). Every public action is re-validated at execution time, so stale approvals fail closed.

## Implementation addendum (FEAT-001, 2026-10-17)
- Peer credentials: uvicorn 0.54 keeps the ASGI app per connection (`H11Protocol.app`). `ossbot.gatekeeper.authz.PeerCredH11Protocol` reads `SO_PEERCRED` once in `connection_made` and wraps that connection's app so every request scope carries `scope["ossbot.peer"]`. Roles map from the peer uid only. The socket is created by the gatekeeper itself with umask 0117 (0660 from the start), group `ossapi`, and handed to `uvicorn.Server.run(sockets=[...])`.
- All endpoints are `async def`, so every SQLite transaction runs on the event-loop thread and transactions never interleave on the shared connection.
- FastAPI 0.143 stores included routers lazily (`_IncludedRouter.original_router`). The route-table test (no approve route, role matrix of §12.2) walks those wrappers.
- Kill/pause on transitions: entry into every working state and into `SUBMITTING` is refused while paused or killed (423). Moves that stop work are allowed: the live-PR redirect into `WATCHING`, any move into `SUBMIT_FAILED`, and `WATCHING` reached from a gate state. Restart reconciliation (M5) needs that last case.
- Resume detection: the enforcer removes the flags; `control.reconcile()` runs at start and every 10 s. It moves `control_state` to `running` only when all flags are absent and either this process wrote `resume-request` or new `resume.log` lines (the offline `ossbot-resume` path, N4) were found in the same pass. Otherwise N12 applies: DB killed without a flag stays killed with an alert, and DB paused without a flag rewrites the flag. `resume.log` is read on every reconcile, not only at start, because a soft-killed gatekeeper keeps running across an offline resume. A partial last line is not consumed, and a file shorter than the stored offset is read from the start.
- The binding for `open_pr`/`push_update` re-derives the bundle, patch and commit-message hashes through an `ArtifactSource` interface. Until the FEAT-002 git TCB provides it, the default `NoArtifacts` raises, so PR-kind approvals fail closed.
- `POST /v1/discovery-requests` creates a `DISCOVERED` contribution with `source='hermes_request'` (for operators too), subject to the same re-discovery rules. There is no separate requests table.
- `POST /v1/actions` is refused (423) while paused or killed. The body is normalized and gets `<!-- ossbot:action=<id> -->` appended at storage time. A secret or Kiro-key hit is reported as anomaly `secret_in_text`: the action is blocked, and a second hit within 24 h pauses.
- The targets denylist no longer carries the work account (no personal values in tracked files). `policy.check_repo` refuses any repo owned by an effective forbidden login (profile union floor) instead.

## Revision 5 amendment (consolidation, 2026-10-18)

Merged from CR-004 incl. Amendment B (DESIGN §9.2, §9.5a, §9.5b, §9.14, §12.6).

- There are now **two deterministic human gates**: gate 1 approves a scouted proposal before any implementation compute is spent (`ProposalApprovals`, ids `p_…`, binding `{proposal_sha256, version, est_class}`), gate 2 is the unchanged public-action approval. Both use two taps on single-use, message-bound tokens; neither can be satisfied by LLM output. Skill activation (CR-002) is a third decision service (`SkillApprovals`, `s_…`); all three are invalidated together by kill and reload (DESIGN §14.18.4.2).
- New states `SCOUTING`, `PROPOSED`, `PROPOSAL_APPROVED`, `PROPOSAL_REJECTED`, `PROPOSAL_SNOOZED`, `PROPOSAL_EXPIRED`, `RESCOPE_REQUIRED`; edges into or out of the gate states are gatekeeper or human only.
- The diff ceiling in `policy.yaml` becomes a runaway-agent guard of 80 files / 3000 non-test lines / 3000 test lines, measured by the gatekeeper with test lines split out; it is config-only (no Telegram path, CR-003 U13) and applies to user-directed work too. Size classes are soft ranking preferences for autonomous discovery only; an overrun is flagged on the preview card, not blocked. The per-target `max_changed_lines` is replaced by per-repo size preferences.

## Implementation addendum (FEAT-006 item 29, 2026-10-18): gate 1 content, size accounting, /work
- `gatekeeper/proposals.py`: `StoredProposals` is the gate-1 content source (table `proposals`, migration `0003_cr004.sql`). The binding is `{v, kind: "proposal", cid, version, proposal_sha256, est_class, user_directed, policy_hash}`, as in §14.11.15. `policy_hash` is the config snapshot hash. `ProposalService` stores scout output (`POST /v1/contributions/{id}/proposal`) and runs Start work, Adjust / Make it smaller / Split, Skip / Later / Never, Undo and the TTL sweep.

The only worker edges near gate 1 are `VETTED -> SCOUTING`, `SCOUTING -> SKIPPED`, the re-scout edges out of `PROPOSAL_SNOOZED`/`PROPOSAL_EXPIRED`, and the guarded `PROPOSAL_APPROVED -> FETCHING`. That edge needs the consumed approval of the current version plus the claim guard. The claim guard moved here from `VETTED -> FETCHING`, which no longer exists.
- The gatekeeper classifies the estimate itself (`size.classify`) and keeps the larger of that class and scout's class. Every proposal above the ceiling is refused (422 `above_ceiling`). Autonomous proposals are also refused above the effective `autonomous_max_class`, for an excluded kind, for a "never" repo, or past `proposal.max_per_day` (429). `👤` items skip all four.
- Size at `/package`: when a first-round (`open_pr`) item hits the ceiling, it pauses in `RESCOPE_REQUIRED` (reason `ceiling`) and a ceiling FYI is sent; nothing is refused or failed. A class overrun does the same only with `size.on_overrun: reapprove`. Otherwise the overrun is only recorded in `size_report_json` for the preview card. Fix rounds (`push_update`) keep the 422 `policy` refusal, so a live PR goes back to `WATCHING` (M4). `RESCOPE_REQUIRED -> PACKAGING` (G) serves Continue and Re-check; the buttons come in FEAT-009.
- `POST /v1/work` accepts only GitHub issue, PR or repo URLs of a configured, enabled target (§14.20.6 regex). It skips the re-discovery history, but an active contribution for the same issue still answers 409. DESIGN does not say whether an unconfigured repo may be used; this build refuses it (`not_a_target`) because the per-repo safety facts (CLA, AI override, egress extras) live in `targets.yaml`.
- `db.migrate` now runs each migration with foreign keys off and requires an empty `foreign_key_check` before COMMIT. This is SQLite's table-rebuild procedure: 0003 rebuilds `contributions` so that `source` can be `'user'`.

## Implementation addendum (post-v1 vet rules, 2026-10-21): AI policy "allowed unless explicitly banned"

Owner decision (2026-10): skip a repo only when it explicitly forbids AI-assisted or AI-generated contributions; silence or ambiguity means allowed, and the card says "AI policy: not stated"; an allow-with-conditions policy is followed in the PR body and checklist. Before this, vet skipped every repo without a policy as `ai_policy_unclear`, and the first live cycles produced no proposal cards. DESIGN §9.4 (M6), §9.5, §12.6, §14.11.1 and §14.11.15 are updated. No I1-I13 invariant changes: the relaxed `check_repo` is a policy choice of the owner, a ban still refuses at vet and at `/package`, and nothing here adds a write path, an approval path or an LLM-controlled decision.

1. One shared module `common/ai_policy.py` (pure, stdlib + pydantic) holds the phrase rules, the classifier, the closed condition kinds, the checklist sentences and the presence check. The runner builds with it (vet, package) and the gatekeeper verifies with the same strings (packaging, cards); `common` depends on no component, so the import-linter contracts are unchanged.
2. Statuses, strongest first: `banned` > `allowed_with_conditions` > `allowed` > `unclear` > `unstated`. Legacy `disclosure_required` reads as `allowed_with_conditions`; a missing status reads as `unknown` (never vetted).
3. A ban from either path wins and the LLM can never weaken it. The vetter's `allowed`/`disclosure_required` claim upgrades the deterministic status only when one of its quotes (≥ 20 characters, whitespace-normalized) occurs verbatim in a fetched repo doc, never the issue or its comments. Issue text such as "AI PRs are welcome" therefore cannot upgrade anything or override a CONTRIBUTING ban (tests `test_issue_claiming_ai_welcome_cannot_override_a_contributing_ban`, `test_issue_text_claiming_welcome_cannot_override_a_contributing_ban`).
4. Sources: CONTRIBUTING, the AI policy file, CODE_OF_CONDUCT, the PR template, `.github/SUPPORT.md`, the README, and the issue body/comments of maintainers (`author_association` OWNER, MEMBER, COLLABORATOR; bans only). Pinned issues need GraphQL, which the read client does not have; not covered deterministically.
5. Config `policy.vet.ai_policy: {unstated: allow, unclear: allow, banned: skip}` (`banned` is `Literal["skip"]`); per target `targets.yaml repos[].ai_policy: {unstated?, unclear?}` (no `banned` key). `ai_policy_override: allowed` and the DB "Allow AI" override allow both, never a ban.
6. Skip reasons: `ai_policy_banned` (never retry, unchanged), `ai_policy_unclear` and new `ai_policy_unstated` (only under a `skip` rule).
7. M6: an `ai_policy_unclear`/`ai_policy_unstated` skip becomes re-discoverable when the effective rule for that status is `allow` (`RepoFactChanges.ai_unclear_allowed`/`ai_unstated_allowed`, computed by the gatekeeper from its snapshot; rule `ai_policy_rule_allow`). Legacy `ai_policy_unclear` rows lift on `unclear: allow`. Re-vet re-classifies, so a real ban still skips. No other M6 rule changes.
8. `check_repo` is rule-aware: `banned` always refuses; `unstated`/`unclear` only under `skip` without an override; `unknown` refuses as `ai_policy_unvetted` unless overridden (no doc was read, so "not stated" can't be claimed; keeps the operator-import semantics).
9. Conditions are a closed set `disclosure | human_review | tool_named | label | title_tag | template_checkbox` with a sanitized value (`[A-Za-z0-9 _:./()\[\]#-]`, ≤ 120, no `@`, no URL, no backticks or `<>`). The package stage adds the `### AI policy checklist` section of fixed sentences before the disclosure block and prefixes the title tag; `/package` refuses `ai_condition_missing:<kind>` when the runner-built text lacks one; the S1 card shows ✅/⚠️ computed on the effective title/body. Labels can't be set by an outside contributor, so that line asks the maintainers (unticked). A PR-template checkbox is ticked only when it is an affirmative AI statement without a negation.
10. The vetter prompt (`prompts/vetter.md`) gains `unstated` and `ai_conditions`. Prompts are baked into the sandbox-llm image, so the probe tuple changes: `ossctl doctor --probes` must pass again after the redeploy.
11. Review pass 1 (2026-10-21): the ban rules also cover the passive and generic-subject forms ("will not be accepted", "won't be merged", "This project does not accept ...", "We are not accepting ...", "made with AI", "ask you not to submit ..."), typographic apostrophes, and conditions/negations are clause-local (split on ", and", ", but", ";", " but "), so a condition in another clause can't cancel a ban. The whole sentence still counts for a ban spanning a list unless it also allows AI. Tests: `tests/unit/common/test_ai_policy.py` `BANS`/`NOT_BANNED`.

CI on PRs (owner decision 2026-10 and its 2026-10-21 amendment; DESIGN §9.4, §9.5, §9.12, §14.11.1, §14.11.11, §14.11.15): repos whose CI runs tests/lint on PRs are preferred, as a ranking boost, never a filter. ## Implementation addendum (discovery pacing, 2026-10-22)

Owner problem (2026-10-22): no autonomous gate-1 proposal all day. Not one discovery cycle had finished since open discovery was deployed (2026-10-21 23:40Z): 87 cycles started, 71 were cut by a `GET /search/issues` 403, 14 by a core 403 and 2 by a gatekeeper 503. Each cut cycle threw away its seed candidates, re-ran about a minute later with a full seed scan (about 4,000-4,800 core requests per hour from the runner alone), and marked the 2 open repos whose issue search worked as `tried` with a 14-day cooldown, burning 142 repos. The open-discovery design's §7.4 assumption "a primary search limit (30/min) is not reachable by the runner alone" was **false in practice**: the per-repo issue search was limited after 2-3 requests per window. Decisions (Part A of the discovery fix; TRACEABILITY `DF-1`…`DF-4`):

1. **A search limit ends only the open phase, never the cycle (DF-1).** `GitHubRead._search` takes an optional `check`; with it, a search-bucket limit of ≤ 65 s (`SEARCH_WAIT_MAX_S`) is waited out outside the search lock in ≤ 5 s slices with `check()` before each slice and after the last, at most twice per call, then the request is sent and GitHub decides. Discovery passes its kill/pause/stop/drain check; scout and `ossctl targets search` pass none and raise at once as before. A longer limit inside the open phase saves `_open.search_until` and raises `OpenEnded` (`OpenResult.ended = "rate_limited"`): the seed candidates and the merge go on. The merge's mention checks (`open_prs_mentioning`) use the same bounded wait; a longer limit there still raises and cuts the cycle, so no contribution is created without its mention check.
2. **`tried` only after the merge used the repo (DF-2).** `OpenPhase._scan` no longer records `tried`; it lists the repo in `OpenResult.scanned`. `od.mark_tried` runs only after a merge that ended normally: a repo is recorded `tried` (cooldown `repo_cooldown_days`) when the merge reached one of its tier-1 picks (mention check, cached refusal or unpaid budget skip, kept across a cut) or when it had no ranked tier-1 candidate; any other scanned repo is re-recorded untried (fresh facts) and carried over. A cut cycle records no `tried`. One-off repair, owner-run only: `ossctl targets discovered --untry --since YYYY-MM-DD` (TTY `UNTRY`) → `POST /v1/discovered-targets/untry` (operator only, `DiscoveredUntry`, extra=forbid) previews, then clears `tried_at`/`cooldown_until` of `candidate` rows tried since that date whose repo got no contribution since, through `discovered_targets_writer.clear_tried` (the writer's import-linter contract is unchanged), with one audit event `discovered_targets_untried` and one FYI. `since` must be within 30 days and not in the future (400 `bad_since`). It widens what discovery may pick, so it is a human go (I9); it was not run by the build.
3. **Issues through the core bucket, labels OR on the client, a core floor (DF-3).** Seed, kept and open repos each cost one `GET /repos/{r}/issues?state=open&sort=updated&per_page=100`; the target's labels (open repos: `discovery.open.issue_labels`) are matched case-insensitively on the client (`od.has_any_label`). A seed target now costs 3 core reads instead of 8. `build_issue_query`, `SearchBudget.issue_search_allowed` and `GitHubRead.search_issues` are removed; search keeps only the topic searches and the mention checks, and `SearchBudget` pays only those. `GitHubRead.core_remaining`/`core_reset` follow core answers' `x-ratelimit-*` headers (`core_left()` is None once the reset passed). While fewer than `CORE_FLOOR = 1000` core requests are left, the seed and kept loops stop, the open phase and CI reads are skipped (CI `unknown`), and the cycle **finishes** with what it read (INFO `discover_core_floor`). Accepted risk: targets late in `targets.yaml` are the ones skipped while the floor holds; at 3 reads per target that should be rare.
4. **A cut cycle resumes (DF-4).** `discover.CycleProgress` (in the scheduler's memory; a runner restart starts fresh) carries the finished seed/kept repos (`done`), their candidates, hashes and size preferences, `seed_finished`, the core-floor flag, the open phase's result and whether it is done, and the reached open repos. A re-run skips finished targets, re-runs the open phase only when it has not run or ended on a search limit (its recorded candidates come back through carry-over), recomputes ranking and CI (cached) and re-runs the merge with the carried `refused` and `created`, each pick with a fresh mention check. A cut resumes no sooner than 1 min (`DISCOVER_RESUME_MIN`) or the rate-limit reset; `github_unavailable` keeps 15 min; a gatekeeper 503 during a full cycle is now a cut too (resume after 5 min, progress kept). Progress older than `interval_hours` is dropped, and a fresh full cycle never starts within 30 min of the previous one's start (`FULL_RESCAN_MIN_GAP`).

No I1-I13 invariant changes: every new GitHub call is a GET on the runner's read client and `github_writer` is still imported only by `submit.py` (I1, I2, I10); kill/pause/stop/drain is checked before every target, search, wait slice, CI read and create (I4); dry-run, both gates, the size ceiling, the review mirror and the state machine are untouched (I3, I7, I12, I13), and no state transition is added; GitHub values stay bounded data, never LLM output (I8); the untry route is operator-only with a TTY confirm, audited and announced (I9, I11). `config/policy.yaml` owner values (`interval_hours`, `repo_cooldown_days`) and rule 13 are unchanged.

Verified facts (web-research rule; checked on 2026-10-22 against the official docs, no token or project data sent):
- [Rate limit endpoint](https://docs.github.com/en/rest/rate-limit/rate-limit): `GET /rate_limit` does not count against the REST primary limit; `resources.core` and `resources.search` are separate buckets (search 30/min in the documented example); the `x-ratelimit-*` response headers are the authoritative source when they disagree with `/rate_limit`; requests authenticated as a user share that user's limit across credentials. So the runner's read token, the gatekeeper's write token and the Hermes GitHub MCP token draw from the owner's one search bucket, the likely "other consumer" the diagnosis could not name (not measured; Part B logs the headers).
- [Search](https://docs.github.com/en/rest/search/search): up to 30 requests per minute for authenticated requests to every search endpoint except code search (10/min).
- [Rate limits for the REST API](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api): headers `x-ratelimit-limit`, `-remaining`, `-used`, `-reset` (epoch seconds), `-resource`; a primary limit answers 403/429 with `x-ratelimit-remaining: 0` (wait for the reset); a secondary limit answers 403/429 with a message saying so (honour `retry-after`, else wait at least a minute and back off). The values can differ between responses (regions), so the floor is a guard, not an exact count.
- [List repository issues](https://docs.github.com/en/rest/issues/issues#list-repository-issues) (OpenAPI description, `rest-api-description`): `labels` is "a list of comma separated label names" and `per_page` is at most 100; GitHub lists pull requests as issues too (discover's `keep_issue` drops them). The docs don't spell out AND for a comma list; GitHub's observed behaviour (6 calls per target in the diagnosis) is AND. The client-side OR filter is correct either way, so the build sends no `labels`.

Part B of the discovery fix (visibility, rate-limit diagnosis, a daily target; TRACEABILITY `DF-5`…`DF-7`):

5. **Discovery is visible (DF-5, fixes 5a-d and 10).** (a) `discover.CycleProgress.stats` (`CycleStats`) counts targets and kept repos read, inactive repos, open repos scanned, seed/kept and open candidates, ranked (both tiers), `scoring.rank` drop reasons, gatekeeper refusals, linked PRs, created items, resumes, the core floor and how the open phase ended, across the resumes of a cut cycle. A finished run logs INFO `discover_done` with every count; `discover_interrupted` gains `cut_reason` (`search_limit` | `core_limit` | `github_unavailable` | `stopped` | `gatekeeper`; `GitHubRateLimited.bucket` tells search from core). (b) The scheduler sends one cycle report per finished or cut cycle to the new worker-only route `POST /v1/discovery-cycles` (`DiscoveryCycleReport`, extra=forbid, every count 0..100,000, at most 12 drop reasons matching `^[a-z0-9_:.-]{1,64}$`, at most 10 cids, `cut_reason` iff `outcome = cut`, at most 120 reports per hour). The gatekeeper audits it as `discovery_cycle` and, for a finished cycle, queues one silent P2 FYI in 📈 OSS feed (category `discovery`, held in quiet hours): `🔎 Discovery · N candidates · created K`, each created cid as a copyable `k.Id` with its subject from the gatekeeper's own `contributions` row, what was read, and the top 3 drop reasons as `k.Text` (redacted, escaped); no buttons. A failed report is logged (`discovery_report_failed`) and never changes the scheduling. (c) The daily digest gains a Discovery block built only from the gatekeeper's tables: cycles finished and cut by reason (the `discovery_cycle` rows), candidates, new `source = 'discover'` items, their gate-1 proposals (`outcomes.proposed_at`), the top 6 terminal drop reasons (`SKIPPED`/`FAILED`/`ABANDONED` by `state_reason`), the scout's on-main skips `already_fixed_on_main` and `not_reproducible_on_main` (fix 10, always shown, 0 included) and discovery stage error classes; a period without a finished cycle shows a warning line. (d) A Telegram background step (`discovery_fyi.watch`) sends one P1 per episode (dedupe key on the last finished cycle, or on the gatekeeper's start when none ever finished) when no full cycle has finished for 12 h, with the cuts since by reason; nothing while killed, paused, draining or down. It runs in the gatekeeper so it also fires when the runner is dead.
6. **Rate-limit diagnosis (DF-6, fix 6).** The `github_rate_limited` log line carries `x-ratelimit-limit`, `-remaining`, `-used`, `-resource` and `-reset` (each cut to 32 characters, None when absent). `GitHubRead.rate_limit()` is a GET of `/rate_limit`; `python -m ossbot.runner.rate_limit` prints the core and search buckets as one JSON line of integers. `ossctl doctor` (full mode) runs it as uid `ossrunner` through `runuser` with `GITHUB_READ_TOKEN` only in the child's environment (never argv or output) and shows `core R/L left (used U, reset HH:MMZ) · search R/L left`: WARN below 1,000 core requests (the discovery core floor) or under 30 searches, FAIL on a failed or garbled answer, SKIP in quick mode.
7. **A daily proposal target (DF-7, fix 7).** `discovery.target_proposals_per_day` (default 2, 0..50, 0 = off, validated `<= proposal.max_per_day`, config-only behind `/reload`, not a Telegram preference). While fewer autonomous first proposals than the target reached gate 1 in the last 24 h (`pacing().used`), `max_per_day` has room and no autonomous item is in `DISCOVERED`, `VETTING`, `VETTED` or `SCOUTING`, the next full cycle runs after `interval_hours / 2` (INFO `discover_early`); a gatekeeper error counts as "not below target". The 30 min re-scan gap still applies. It never raises `max_per_day` or the size ceiling, which scout and the proposal submit still enforce. `config/policy.yaml` gains only this key at its default. Consequence: a policy with `proposal.max_per_day` below 2 must now also lower `target_proposals_per_day` (the live config has 5).

No I1-I13 invariant changes in Part B either: the only new route is a worker-only Unix-socket route that records and notifies, with no transition, approval, control or config effect (I3, I9, I13); every new GitHub call is a GET (`/rate_limit`) on the runner's read client (I1, I2); the FYI and the stall warning have no buttons, take subjects from the gatekeeper's own rows and render runner data only escaped (I8, I12); the audit rows go through `audit.append` in a transaction (I11); kill and pause still stop discovery at every target, and the stall warning is silent while stopped (I4); dry-run and the ceiling are untouched (I7). No exposure: no inbound port, webhook or tunnel.

Verified facts for Part B (web-research rule; re-checked on 2026-10-22 against the official docs, no token or project data sent):
- [Rate limit endpoint](https://docs.github.com/en/rest/rate-limit/rate-limit): the answer is `resources.{core,search,…}.{limit, used, remaining, reset}` (the closing-down `rate` object duplicates `core`); its documented example shows `search.limit = 30`.
- [Rate limits for the REST API](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api): `GET /rate_limit` does not count against the primary limit but can count against the secondary limit, so doctor calls it once per run.
- [Search](https://docs.github.com/en/rest/search/search): the documented search limit is **30 requests per minute** authenticated (code search 10/min; semantic and hybrid issue search 10/min, which ossbot never sends).
- Measured 2026-10-22 (V-B, close-out; source: live `GET /rate_limit` as ossrunner through `ossctl doctor`, full mode, after the redeploy at 15:38Z): **core limit 5,000/h, search limit 30/min**, so the documented values hold for the read token. At 15:39Z core showed `used 4407` (593 left, reset 15:41Z): the quota drained by the pre-fix retry loop, so doctor WARNed and the first post-redeploy cycle stopped at the core floor (623 left) and still finished. At 15:41Z, after the reset: core `used 2` (4,998 left), search `used 0` (30/30 left), doctor all PASS. The search limit itself is the documented 30/min, so the tight issue-search limit seen on 2026-10-22 came from consumption of the shared account bucket (V-A 1) or a query-shape secondary limit, not from a lower limit (inferred; not reproduced). With issues read through the core bucket (fix 3) discovery no longer sends issue searches.
