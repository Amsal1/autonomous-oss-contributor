# ADR-0025: Egress mode `sandbox_full`: full public web for repo code, the floors as the safety line (amends I5, ADR-0023, ADR-0024)
Status: Accepted (owner decision 2026-10-23/24, "I want to be minimal blocker … All we need to ensure is its limited to WSL/sandbox environment") · Design: DESIGN.md §8.3, §8.4, §10.3, §10.4, §11.1, §11.3, §11.4, §11.5, §11.6, §13.6; .ossbot-local/postv1/build-env/design.md · Amends: ADR-0005 (I5), ADR-0023, ADR-0024 · Related: ADR-0013, ADR-0017

## Context
In `sandbox_open` with `implement_network: auto`, builds still failed for reasons the owner calls "network": proxy-unaware tools (a JVM, git, curl in a build script, toolchain installers) had no resolver and no route; validate ran Gradle offline; a `needs_network` after a networked coder run was terminal; JDKs and other toolchains the image lacked had no install route; volume limits held contributions that were just big builds. The owner accepts that repo code and LLM-chosen commands reach the public web. His line is: nothing outside the distro and its containers is reachable — not his Windows host, not his LAN, not the distro's own services — and no credential sits next to repo code.

Glossary: the egress **mode** `sandbox_full` is unrelated to the **image** key `images.sandbox_full` in `config/versions.lock.yaml` and the image `ossbot/sandbox-full`; the two never share a file.

## Decision
- **A fifth mode `sandbox_full`** after `sandbox_open`, with the same squid rules (the schema requires `modes.sandbox_full == modes.sandbox_open`, the renderer asserts the contexts are equal but the label). Switching to it is a human go action (Telegram `/egress`, two taps; `ossctl egress mode sandbox_full`, TTY confirm), audited and announced; it also raises `implement_network` to `auto` when lower. Until the owner's `/reload` loads a snapshot with `modes.sandbox_full`, the mode can't be selected; the floors don't wait for the reload (the built-ins are unioned).
- **`mode_default` stays `open`** (a deviation from the brief's "allowlist", recorded on purpose): in `open` no repo-code pool gets `web_public`, so a fresh install is as conservative for repo code as `allowlist`; `open` keeps web search for the LLM roles. The owner can set `mode_default: allowlist` with one line and `/reload`.
- **Proxy-unaware tools in every mode** through an untrusted in-sandbox shim, `ossbot-netshim` (stdlib, in the repo-code image only): a stub DNS on `127.0.0.1:53` that answers every external name with a per-name `127.70.x.y` address and never forwards, and 80/443 listeners that turn each connection into an ordinary `CONNECT` / absolute-form request to `proxy:3128`. Networks stay `--internal` without a route; squid stays the only way out and keeps logging names and bytes per job. `NO_PROXY=localhost,127.0.0.1,::1,.localhost` keeps a repo's own test servers local.
- **The floors are the safety line**: RFC1918, CGNAT, link-local and cloud metadata, loopback, `198.18/15`, `192.0.0/24`, multicast, reserved, `::`, `::1`, ULA, IPv6 link-local and multicast, NAT64 and 6to4 (`64:ff9b::/96`, `2002::/16`), the live host addresses (rendered into squid and the kernel from `ip` and `/etc/resolv.conf` at render time; a change is `firewall_drift:host_floor_changed`), **the owner's own public address(es)**, the distro's sockets and ports, the always-denied names, and for repo code Telegram and every Kiro host (`code_denied`). Built-ins are unioned with the config, which can only add.
- **The public address is learned and fails closed.** A root timer (`ossbot-pubip`, every 60 s) asks two providers from the distro's own network stack (`https://1.1.1.1/cdn-cgi/trace`, `https://checkip.amazonaws.com/`), keeps the union of valid public answers for 24 h (at most 8 per family), and enforces them in squid (the file ACL `/etc/squid/floor/public.txt`, re-read on SIGHUP from a directory bind) and in a kernel chain (`OSSBOT-PUBFLOOR`, jumped first from `OSSBOT-FWD`, updated make-before-break). These requests are a new outbound flow of root: a fixed GET with the User-Agent `ossbot-pubip`. While no answer is fresher than five minutes, repo code gets no public web in either web mode (`code-web.txt` holds a sentinel, so squid's `code_web` allow lines match nothing), sandboxd refuses web jobs with 503 `public_floor_unknown` and stops running ones, and the runner defers them (never a failure); the owner gets one P1 notice after 10 minutes. The value appears in no log, audit row, card, digest or tracked file ("your public address").
- **One root-only lock for the floor.** Every writer and checker of the public floor serialises on `/etc/ossbot/proxy/floor/.lock` (`flock(2)`, `0600 root:root`, in the `root:root 0755` floor directory, opened `O_NOFOLLOW`; an untrusted file or directory is refused with ERROR `floor_lock_untrusted` and the caller fails closed): `ossbot-pubip`, `ossbot-firewall --apply` for the parts touching `OSSBOT-FWD`/`OSSBOT-PUBFLOOR` and `render squid`'s floor-file creation take it exclusively; `--check` and the watchdog's `squid_drift` take it shared with a 10 s timeout. No non-root user can create, open or hold it.
- **Two independent layers per IP floor and path.** For the sandbox's own packets: no route, the distro firewall (`OSSBOT-IN`, `OSSBOT-FWD`) and the Docker filter's network shapes. For squid's upstream connections: squid's destination ACLs **and** a kernel NEW-state drop in `OSSBOT-FWD`/`OSSBOT-PUBFLOOR` (forwarded) and `OSSBOT-IN` (a distro-local address) for every new connection from the proxy network to a floor address, because a name can re-resolve between squid's check and its connect (DNS rebinding, ipcache expiry). Names have one network layer (squid); the second line is that repo code holds no credential. The same kernel drops apply to `10.211.0.0/24` (image builds) and `10.214.0.0/16` (root-created networks).
- **Any floor attempt holds, in every mode.** Marked by squid on any port (the marked sandbox denies come before the port checks), or dropped and logged by the kernel (sandbox → host `in` lines; the live proxy → floor `px` lines, only from `10.212.0.2`; authoritative), or, supplementary, seen as squid's server address: the job stops and the contribution is held with reason `egress_floor` and a P1 card that names what was tried in plain words. Kernel log lines are split by source: drops by root's test proxies on the same bridge are `tx` lines and never hold or notify. A `px` line with no job running is a P1 notice. Names and literals that resolve to loopback and the HashiCorp checkpoint beacon are denied and noted, not held.
- **Volume is a note in `sandbox_full`.** A web job's host-count, upload or download breach of `egress.anomaly` no longer stops the job or holds the contribution when the job started in `sandbox_full` and the mode is still `sandbox_full`; sandboxd posts a note (`POST /v1/contributions/{cid}/egress-notes`) that the gatekeeper stores and shows in the daily digest. `allowlist` … `sandbox_open`, base jobs and strict jobs keep the ADR-0023 holds; a narrowing switch restores the hold for a running job at once.
- **I5 text.** "… egress only through the proxy (also for proxy-unaware tools, via the in-sandbox shim) with a per-profile list; in egress modes `sandbox_open` and `sandbox_full` `fetch`/`validate`, and `agent-exec` when `implement_network` allows it, also get `web_public` behind the always-denied floors; any attempt to reach a floor holds the contribution in every mode; in `sandbox_open` the per-job volume limits also hold, in `sandbox_full` they are notes; repos with `egress: strict` keep the base list in every mode and their `agent-exec` never gets a network …" The credential half is unchanged and absolute.
- **ADR-0024's table** reads "egress mode ∈ {sandbox_open, sandbox_full}" where it read "sandbox_open".
- **The base lists grow** (named on purpose): `fetch` and `validate` gain the category `pkg_toolchains` (JDK metadata and vendor hosts, the foojay API) and `pkg_rust` gains `static.rust-lang.org` when the toolchain resolver lands. Base lists apply in every mode and to strict repos, so "a strict repo gets nothing beyond the base list" means this larger list. Every installer that uses them checks a published checksum or is pinned by one.

## Alternatives
- Redefine `sandbox_open` as full: removes the guard the owner chose for the mode he runs and makes "full" a two-key rule. Rejected.
- iptables REDIRECT to squid with SNI peek/splice: a squid package switch (OpenSSL build) in the TCB, a routed network shape, policy routing into squid's netns, and a real resolver for sandboxes (a DNS exfiltration channel). Rejected.
- Direct NAT egress with iptables drops: the floors collapse into one iptables layer, names disappear from the log, a new byte meter and a resolver are needed. Rejected.
- Drop the guard entirely in `sandbox_full`: loses the floor alarm the owner named as his safety line. Rejected.

## Consequences and residual risks
- Repo code can send arbitrary bytes to any public host on 80/443 from the owner's IP for the job's lifetime; bounded by the floors, the job timeout and the kill switch, not by volume. A slow or large leak of public repository data is possible; there are no secrets in those containers.
- Third-party abuse from the owner's IP (scanning, spam through public HTTP endpoints) is bounded only by the job timeout and 80/443.
- A `connect()` to an IP literal fails inside the container (no route) and is observable nowhere; it reaches nothing.
- The public-address floor has a window after the owner's address changes — **≤ 60 s while the providers answer, at most 360 s otherwise** — in which an already running job could reach the new address before it is floored; it is detected afterwards from squid's log by the late check (a ring buffer of ≤ 50 000 entries / 10 minutes; when full, the oldest entries go first, counted in `late_check_evicted` with one INFO line per affected job) and held. Router addresses never used for egress are not learned; a Windows global IPv6 address isn't learned, but no IPv6 path exists from squid or a sandbox. Optional owner hardening on the Windows side: backlog W-1 (Hyper-V allow rules restricted to public ranges, `LoopbackEnabled False`).
- If both address providers are unreachable for five minutes while the internet otherwise works, repo code's web pauses (deferred jobs, a P1 notice) until one answers.
- Repos whose own tests call Telegram or Kiro hosts get held in web modes; the owner can release and mark the repo strict.
- A kernel drop of squid's connection to a floor can't name the job that caused it (the source is squid), so every metered job running at that moment is held; with none running, the owner gets a P1 notice. This needs a DNS answer that changes between squid's check and its connect, so it should be rare; over-holding is the safe side.
- netshim makes proxy-unaware connection attempts visible to squid, so in modes with volume holds a denied name that used to fail at DNS inside the container now counts toward `max_hosts`. More signal, not less.
- Builds may pull new code from the web into the diff; gate 2 shows the diff and says when the coder had network.

## Verified facts (2026-10-24)
Design §16: Docker 29.9.1 embedded DNS forwarding to `127.0.0.1:53` in the container netns and `ip_unprivileged_port_start=0` (V-D1, V-D2), squid 6.14 `annotate_transaction` / `%note` (V-S1) and SIGHUP = reconfigure (V-S4), the WSL NAT host address, the Hyper-V `LoopbackEnabled` meaning, the two public-address providers (V-P1). Live after the deploy of 2026-10-24 (FEAT-002):
- **L-2** netshim receives the forwarded query on an internal network: `getent hosts example.com` answers from `127.70/16` in every networked repo-code shape, and `curl --noproxy '*'`, `git ls-remote`, a Java `HttpURLConnection` with `Proxy.NO_PROXY` and a build script's curl reach allowed hosts through squid (`tests/sandbox/test_proxy_unaware.py`).
- **L-3** `journalctl -k` shows `OSSBOT-FLOOR-IN=`, `OSSBOT-PFLOOR-IN=`/`OSSBOT-TFLOOR-IN=` lines, and `ossbot-floorlog` writes `in`/`tx` lines (`tests/system/test_floor_reach.sh`).
- **L-8** a no-cache image build on `docker0` that fetches from PyPI succeeds with the `10.211.0.0/24` and `10.214.0.0/16` drops in place, and neither a build nor a root-created network reaches `10.0.0.1` or `169.254.169.254`; no exemption was needed.
- **L-10** squid logs the server address `%<a` even for a CONNECT whose upstream SYN the kernel dropped (`TCP_TUNNEL/503 <address>`), so the supplementary server-address row also sees a dropped rebinding; the kernel lines stay the authoritative signal.
- **L-11** a rename inside the directory-bound `/etc/squid/floor/` followed by SIGHUP makes squid apply the new `code-web.txt` and `public.txt` (step 4b of the floor-reach test on a test proxy).
- **L-13** `ossbot-pubip` as root in the distro's host netns gets valid answers from both providers, and the live floor equals the Windows-side answer (compared without printing).
