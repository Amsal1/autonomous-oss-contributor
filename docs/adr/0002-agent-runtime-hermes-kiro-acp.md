# ADR-0002: Agent runtime is Hermes (OSS-side role narrowed; general multimodal assistant since rev 5) with a vendored kiro-acp provider, V3 ACP primary
Status: Accepted (amended in design rev 5 on 2026-10-18; revised in design rev 1, rev 2, rev 3 and rev 4) · Date: 2026-10-17 · Design: DESIGN.md §15

## Context
The user wants a conversational agent on Telegram with memory and room for future integrations, using unlimited Kiro access through the official CLI only. MITM model routers (9router, OmniRoute) are rejected for ToS reasons. User decision (2026-10-17): Hermes uses Kiro **V3 ACP** as primary.

Live doc check (kiro.dev/docs/cli/v3/acp-migration, 2026-10-17): launch `kiro-cli acp --agent-engine=v3`; v2-only flags `--agent --model --effort --trust-all-tools --trust-tools` rejected; capabilities negotiated via `initialize` and `agentCapabilities._meta.kiro.extensionMethods`; `session/new` accepts `_meta.kiro.{modeId, modelId, effortLevel}`; model via `session/set_config_option configId:"model"` (no `session/set_model`); default auth = CLI login, `--auth-method=client` → `_kiro/auth/getAccessToken`; permissions via standard `options[]`. The page does not mention `KIRO_API_KEY`.

## Decision
- Hermes Agent pinned to `v0.22.2`, Unix user `hermes`, API-server platform only (the Telegram bot belongs to the gatekeeper, ADR-0004).
- Provider: fork of `tobenwarrior/hermes-kiro-provider@02c4dd06585436751145961658a22b773f23a0ef` vendored at `vendor/hermes-kiro-provider/` (`UPSTREAM_COMMIT`, own history), with a separate V3 adapter beside the original V2 code.
- V3 adapter: launch without v2 flags, cwd outside any repo, handlers registered before `session/new`, capability-gated optional calls, live model/effort switch from `config/models.yaml` via `set_config_option`, turn completion from the prompt response only, `session/load` on reconnect without resending prompts.
- Permission requests are always answered by deterministic code with a reject option (or `cancelled`), never with consent metadata. Kiro-side deny rules for `hermes` stay as defence in depth.
- (rev 2) Hermes's own tool surface is an allowlist (memory, todo, session_search, ossbot), enforced at runtime by the gatekeeper via `GET /v1/toolsets` with a kill on drift (ADR-0018). The `ossbot-chat` Kiro agent has only `web_search`/`web_fetch`. `~hermes/.kiro/settings/cli.json` disables knowledge and code intelligence. No auth option keeps the key away from the `hermes` uid; the control is that no model-reachable tool reads files or runs code.
- Auth order, each proven by live probe: (a) `KIRO_API_KEY` with default auth; (b) `--auth-method=client`, shim answers `getAccessToken` from `hermes.env`, token never logged; (c) device-flow login as `hermes`.
- Fallback 1: V2 ACP via the original plugin path. Fallback 2: per-turn `kiro-cli chat --v3 --no-interactive` provider. Last resort: replace Hermes behind the gatekeeper's `ChatBackend`.
- Upstreaming the V3 adapter is the first candidate contribution, via `ossctl contribution import` and normal approval.

## Revision 3 amendments (design review round 3, M9/M10)
- M9: the V3 adapter fails closed on its session surface. After `session/new` and `session/load`, the current mode must be `ossbot-chat`. Where V3 advertises a tool list, it must be ⊆ {`web_search`, `web_fetch`}. Otherwise the adapter refuses the turn and its `on_surface_violation` hook (set by ossbot to a gatekeeper UDS kill) soft-kills with `hermes_kiro_surface`.
- M9: a root helper, `ossbot-hermes-probe`, acts as the ACP client with the adapter's own launch and session parameters (code origin and key refined in rev 4, R4-M2 below). It runs a `research_deny`-style probe (read the env, `hermes.env` and `cli.json`, run `id`, `web_fetch` the contents) and evaluates the stream deterministically. The result is keyed by `(kiro_cli_version, hermes_agent_sha256, permissions_sha256, settings_sha256)`. The gatekeeper enables the chat relay only while a pass younger than 2 h exists. Neither Hermes nor the gatekeeper can forge the result.
- M10: Hermes is installed from `git clone --depth 1 --branch v0.22.2`. The annotated tag object and the peeled commit are verified against `versions.lock.yaml`, then `uv sync --frozen --no-dev` runs as `hermes`. The website installer is never used, and `setup-hermes.sh` is not executed (its non-dependency steps are reproduced in `provision.sh`). `ossctl hermes upgrade` takes the same path.
- **Addendum slot (implementation):** the peeled commit, the list of reproduced `setup-hermes.sh` steps, and the observed `modes.currentModeId` and tool-list fields for `modeId: "ossbot-chat"`.

## Revision 4 amendments (design review round 4, R4-M2/R4-N4)
- R4-M2: no hermes-writable byte ever runs as root.
  - The root probe runs `/opt/ossbot/app/.venv/bin/python -I -m ossbot.ctl.hermes_probe` with cwd `/`.
  - It imports `kiro_acp.v3_core` (stdlib-only launch, session and surface logic, no Hermes imports) only from the root-owned copy `/opt/ossbot/app/vendor/hermes-kiro-provider/` (root:root, 0755/0644). It never imports from, or adds to `sys.path`, anything under `/home/hermes`.
  - It hashes the deployed `~hermes/.hermes/plugins/model-providers/kiro-acp/**` (regular files, `O_NOFOLLOW`, sorted paths) against the root copy. A mismatch or a link fails the probe with `adapter_drift`.
  - The probe key becomes `(kiro_cli_version, hermes_agent_sha256, permissions_sha256, settings_sha256, adapter_sha256)`.
  - Hermes-owned executables run only via `runuser -u hermes --`, and hermes-owned files are only hashed, never executed or acted on as config.
- R4-N4: the Hermes install clones and verifies in root-owned `/var/lib/ossbot/staging/hermes-<tag>`.
  - It runs `chown -R --no-dereference`, then swaps with `mv -T $D $D.prev; mv -T staging $D`. `uv sync --frozen` then runs as `hermes` at the final path, because venvs are not relocatable, and a failure rolls back to `$D.prev`.
  - Before touching `~/.hermes`, the step stops Hermes, kills every `hermes` process, and refuses if any path involved is a symlink.
## Alternatives
- OpenClaw: rejected in the brief; trust concerns would be the same, which is why neither is a safety boundary.
- No framework: loses memory/skills/future integrations the user asked for.
- Third-party "Kiro gateway" bridges: rejected (unvetted, router-like).

## Consequences
We own a small fork. The plugin has one maintainer and no users; contract tests against `tests/fakes/fake_acp_v3.py` and a doctor round-trip guard upgrades. **Build-time probe (to append here at implementation):** real `kiro-cli acp --agent-engine=v3` initialize + session/new transcript (redacted), advertised extension methods, mode/model options, and which auth option worked.

## Revision 5 amendment (consolidation, 2026-10-18)

Merged from CR-002 incl. Amendment A (DESIGN §15.5, §15.6) and the user's chat decisions (DESIGN §25).

- Hermes's role widens from "narrowed chat front-end" to the user's **general-purpose multimodal assistant**: every non-command Telegram update (text, photos, albums, documents, voice, locations, quoted replies) is relayed to it; answers stream with sources; features ship as skills or `ossbot` plugin tools with per-feature SQLite stores; a reverse-image-search provider is a documented hook only until the user picks one. The gatekeeper still owns the bot, the deterministic commands and every public GitHub write.
- Capability tiers `locked` / `research` / `self_improve` (default `self_improve`) replace the single allowlist (ADR-0018 amendment). Self-written skills are staged inactive and activated only through a two-tap Telegram skill card; root copies the bound bytes into a read-only active dir. `terminal`, `code_execution`, `file`, `browser`, `delegation` and `cronjob` stay off in every tier; code runs only as gatekeeper-scheduled sandbox jobs.
- Images go to the model as ACP image content blocks when V3 advertises `promptCapabilities.image`, on the new `vision` role (ADR-0009 amendment); attachments are downloaded by the gatekeeper with a size cap, a type allowlist and metadata stripping without Pillow (ADR-0020).
- Unchanged and re-affirmed: the vendored fork of `tobenwarrior/hermes-kiro-provider` on Kiro **V3 ACP** is primary, V2 ACP is the fallback, and the fork's V3 adapter is queued as the first upstream contribution through `ossctl contribution import`; pipeline roles run `kiro-cli chat --v3 --no-interactive`.

## Implementation addendum (FEAT-007 item 33, 2026-10-18): research before coding

Sources, all fetched 2026-10-18: the Kiro release manifest (`desktop-release.q.us-east-1.amazonaws.com/latest/manifest.json`); the Kiro docs as Markdown twins (the HTML pages are client-rendered; `kiro.dev/llms.txt` says every page has a `.md` twin): `docs/cli/v3/acp-migration.md`, `docs/cli/acp.md`, `docs/cli/headless.md`, `docs/getting-started/authentication.md`; Hermes `v0.22.2` read from a `--depth 1` clone of the tag (source files and `website/docs/**` at the pinned commit). The live V3 handshake, auth and web-routing checks follow in the item 35 and item 38 addenda.

Kiro CLI (§23 items 10, 11, 12, 5c):
- Manifest latest is still **2.32.0** (headless tarGz sha256 `05989f9b…d312`, unchanged). CLI 3.0 is not out, so the pin stays and §23 item 12 stays open; `--agent-engine=v3` is the documented V3 ACP launch.
- V3 ACP launch: `kiro-cli acp --agent-engine=v3`; the v2-only flags `--agent`, `--model`, `--effort`, `--trust-all-tools`, `--trust-tools` are rejected. Default auth is the CLI login; `--auth-method=client` makes the client answer `_kiro/auth/getAccessToken` (the V3 overview also names `--auth-method=cli`, the explicit default). Neither page mentions `KIRO_API_KEY` for ACP; the auth page says the key covers "all Kiro CLI features available in non-interactive mode" and that a CLI login takes precedence over the key. Option (a) vs (b) is therefore decided by the live probe (item 35); the response shape of `getAccessToken` is not documented.
- Transport NDJSON JSON-RPC 2.0. `session/update`, `session/request_permission` and (with client auth) `_kiro/auth/getAccessToken` must be registered before `session/new`/`session/load`; any agent-to-client request with an `id` needs a result or an error. Optional methods are gated on `agentCapabilities._meta.kiro.extensionMethods`, never on the version (both generations negotiate `protocolVersion` 1).
- `session/new` / `session/load` take `cwd`, `mcpServers`, `additionalDirectories` and `_meta.kiro.{modeId, modelId, effortLevel}`; the client re-sends `cwd` and `mcpServers` on load. Model and effort change with `session/set_config_option` `configId` `model` / `effortLevel` (no `session/set_model`); mode with `session/set_mode` or a `mode` config option. Mode changes arrive as `current_mode_update`, config changes as `config_option_update`. The response field names for the current mode and whether a tool list is advertised are not documented (the CLI ACP page lists only `loadSession` and `promptCapabilities.image: true` as advertised capabilities); the live handshake records them.
- Turns settle only on the `session/prompt` response; `session_info_update` `turn_end` is not completion. After a transport drop: re-register `session/update`, `session/load`, never resend the prompt.
- Permissions: `options[]` is authoritative; never synthesize an option; persistent choices would need `_meta.kiro.consent`, which ossbot never returns. MCP annotations are untrusted claims; failed tool updates may carry `_meta.kiro.failureReason`.
- 5c: the docs give no ACP-specific equivalent of `chat.enableKnowledge` / `chat.enableCodeIntelligence`; V3 non-interactive runs read the saved settings (`~/.kiro/settings/cli.json`), and the V3 harness is shared by `chat` and `acp`. The hermes-side `cli.json` is the sandbox copy (both off); the Hermes-side probe asserts the tool surface either way.
- Image prompts: `promptCapabilities.image: true` is documented; audio is not mentioned (decided live in item 38, §23 item 30).

Hermes v0.22.2 (§23 items 13, 28, 29, 30):
- Peeled commit `d923a5eb487a17c0a68801bba9ef0f56c81040a8` (tag object `7b77e29e…46f6` matches), recorded in `config/versions.lock.yaml`. `requires-python = ">=3.11,<3.15"`, `.python-version` 3.14; entry points `hermes = hermes_cli.main:main` (also `hermes-agent`, `hermes-acp`).
- `setup-hermes.sh` (not executed). Its steps: (1) stage the pinned uv from `pm/lock.json`; (2) `uv python install` and `python -m pm.cli install` (dependencies, hash-verified from `uv.lock`); (3) copy `.env.example` to the checkout's `.env` (chmod 600); (4) publish launchers into `~/.local/bin` via `hermes_cli/_launchers.py`; (5) add `~/.local/bin` to the shell rc; (6) seed bundled skills into `~/.hermes/skills/`. ossbot reproduces only (4), as a `~/.local/bin/hermes` symlink to `~/.hermes/hermes-agent/.venv/bin/hermes`; dependencies come from `uv sync --frozen --no-dev` with the pinned uv and a managed CPython (step 2 equivalent, locked); (3) and (5) are not needed (the unit passes the environment and the full path); (6) is deliberately skipped because no skill is active without approval.
- Config keys (all in `hermes_cli/config_defaults.py`): `approvals.mode` (`smart` default; `manual` used), `approvals.cron_mode: deny`, `approvals.unattended_mode: deny` (the v1 names are right); `updates.check: false` and `plugins.auto_update_check_hours: 0` turn off the passive update checks (there is no auto-apply of Hermes itself); `curator.enabled` (default true; ossbot sets false); `platform_toolsets.api_server` is the API-server key (`_get_platform_tools(config, "api_server")`); `agent.disabled_toolsets` applies after it.
- Tool Search: `tools.tool_search.enabled` default `"auto"`; the loader maps a YAML boolean `false` (what an unquoted `off` parses to) to `"off"`, and `off` means "pass-through, no bridge". The template writes the string `"off"`.
- `GET /v1/toolsets` returns `{"object": "list", "platform": "api_server", "data": [{name, label, description, enabled, configured, tools}]}`: the documented per-entry fields inside a `data` envelope (the docs page shows a bare list). Only configurable and plugin toolsets are listed, each with the tools it expands to. The surface check parses the envelope (`extra="ignore"` per N7).
- `/v1/responses`: `input[].content` parts `input_text` and `input_image` (`image_url` as an https or `data:image/...` URL); `input_file`/`file_id` and non-image data URLs are refused with 400 `unsupported_content_type`, so PDFs and text files are sent as extracted text. `stream: true` returns SSE `response.created`, `response.output_text.delta`, `response.output_item.added`/`done` (incl. `function_call` items), `response.completed`, with `: keepalive` comments every 10 s. `conversation: <name>` chains turns server-side; `X-Hermes-Session-Key` (≤ 256 chars, no control characters) scopes long-term memory; `POST /v1/runs/{id}/stop` cancels a run. `API_SERVER_ENABLED`, `API_SERVER_KEY` (required), `API_SERVER_HOST` (default 127.0.0.1) and `API_SERVER_PORT` (8642) are env vars.
- Model-provider plugins: `$HERMES_HOME/plugins/model-providers/<name>/__init__.py` is imported and calls `register_provider(profile)`; `auth_type="external_process"` with `create_client()` returning an OpenAI-client facade (`chat.completions.create`). Upstream `hermes-kiro-provider@02c4dd06` is that shape: its `KiroACPClient` subclasses Hermes' in-tree `CopilotACPClient`, which spawns one ACP process per completion, renders the transcript and Hermes' own tools into one text prompt (`agent.acp_openai_bridge`), parses `<tool_call>` blocks back, and advertises `clientCapabilities.fs.readTextFile/writeTextFile` with a file bridge confined to the cwd. The V3 adapter keeps the bridge helpers (text rendering only) but advertises no client capabilities: no `fs`, no `terminal`; every `fs/*` or `terminal/*` request gets `-32601`. So no file bridge reaches the agent. `kiro_acp/v3_core.py` needs nothing from Hermes (argv, params, surface and permission logic, NDJSON framing), as §23 item 13 expected.
- Skills (§23 item 29). Search roots, in precedence order: trusted project dirs (`skills.project_discovery`, only for roots in `skills.trusted_project_dirs`), the local `~/.hermes/skills/`, `skills.create_dir` (a search root too, so it cannot be a staging dir), `skills.external_dirs`. `skill_manage` creates under `create_dir` or the local dir and edits a skill where it is found. **v0.22.2 keeps staged and active apart:** with `skills.write_approval: true` every `skill_manage` mutation (create, edit, patch, delete, write_file, remove_file, batch operations; foreground and the background review alike) is staged as a JSON record `~/.hermes/pending/skills/<id>.json` holding the exact replay payload, and nothing is written to a skill root; pending records are not a search root. ossbot uses that as the staging area (instead of the `~/.hermes/skills-staging/` file tree named in §15.5): the root hasher reads the records as untrusted data, materializes the proposed files from the active copy plus the operations, and binds their hashes; on Confirm root writes exactly those bytes into `~/.hermes/skills/`, which is `root:hermes` 0750/0640, so a Hermes bug that bypassed the gate would still fail with `EACCES`. The gate keys are pinned in Hermes' **managed scope** (`/etc/hermes/config.yaml`, root:root 0644, documented to win over `~/.hermes/config.yaml` and the environment per leaf; lists are replaced whole). `curator.enabled: false`, `skills.project_discovery: false`, `skills.create_dir: ""`, `skills.external_dirs: []`, `skills.inline_shell: false` and `skills.ledger: false` are pinned too. `HERMES_MANAGED_DIR` would redirect the managed scope and `~/.hermes/.env` is loaded with override, so the `hermes` step installs a root-owned `~/.hermes/.env` and doctor checks its hash.
- Web tools (§23 item 29, `research` tier): the `web` toolset (`web_search`, `web_extract`) defaults to a keyless rotation over vendor APIs (Exa, Parallel, Firecrawl, Keenable). The clients honour `HTTPS_PROXY` (`tools/url_safety.py` delegates DNS to the proxy when it is set), and OSSBOT-OUT lets uid `hermes` reach only `10.212.0.2:3141` and `lo`, so any Hermes web call either goes through squid 3141 or fails. `HERMES_WEB_VIA_PROXY` is set to true: `research` = `locked` + `web`, `self_improve` = `research` + `skills`. The squid-log confirmation is in item 38. Search queries go to those vendors' free tiers; `web.keyless_fallback: false` would turn that off.
- State layout (§23 item 28) under `~/.hermes/`: `config.yaml`, `.env`, `SOUL.md`, `memories/` (MEMORY.md, USER.md), `sessions/`, `state.db` (sessions and gateway state), `response_store.db` (`/v1/responses` chains), `skills/`, `pending/{skills,memory}/`, `cron/` (unused), `logs/`, `plugins/` (model providers, the ossbot plugin), `hermes-agent/` (the code tree, not state). The live tree is recorded after the install (item 35) for FEAT-008's backup list.
