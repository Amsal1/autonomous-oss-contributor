# ADR-0021: Windows shutdown hooks: a per-user shutdown blocker (6a) and a User32 1074 event task (6b)
Status: Accepted (2026-10-19, FEAT-008 items 40-41) · Design: DESIGN.md §13.5 (CR-001 6), §4 NFR-3 · Related: ADR-0008 (kill and lifecycle), ADR-0016 (bootstrap) · Verify: DESIGN §23 item 31 (the real restart, FEAT-011 item 57)

## Context
Windows 11 Home (this laptop: build 26100, Windows PowerShell 5.1.26100) has no Group Policy shutdown scripts. When Windows shuts down, restarts or signs out, the WSL utility VM is stopped with the session; ossbot then loses the work in flight (crash safety, §13.5 (c), recovers it, but a graceful `down` sends the "Going down" summary, lets running jobs finish and records the shutdown type). CR-001 6 asks for two hooks: (a) a blocker that holds the shutdown while `down` runs, and (b) an event-triggered task as a best-effort backup.

## Research (2026-10-19, web, recorded before the code)
- `WM_QUERYENDSESSION` is sent to every top-level window when the user ends the session or a program calls a shutdown function; returning 0 stops it ([WM_QUERYENDSESSION, Microsoft Learn](https://github.com/MicrosoftDocs/win32/blob/docs/desktop-src/Shutdown/wm-queryendsession.md)). Since Vista an application may delay its answer; after 5 s Windows shows a full-screen list of the applications that block, with their registered reasons, and the user can continue or cancel ([Shutdown Changes for Windows Vista](https://learn.microsoft.com/en-us/windows/win32/shutdown/shutdown-changes-for-windows-vista)).
- Console applications and applications **without a visible window** cannot block: they are terminated if they do not answer within 5 s (same page). So the blocker window must have `WS_VISIBLE`; it can be off-screen and kept out of the taskbar (a tool window), but not hidden.
- `ShutdownBlockReasonCreate(hWnd, reason)` takes the application's main window and must be called on the thread that created it; `ShutdownBlockReasonQuery` has the same thread rule ([Create](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-shutdownblockreasoncreate), [Query](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-shutdownblockreasonquery)). A test from another process therefore cannot query the reason itself; the blocker queries it on its own thread and reports the result (log and state file).
- A process that loads user32 is treated as a Windows application: its console control handler does not get `CTRL_LOGOFF_EVENT`/`CTRL_SHUTDOWN_EVENT`, it gets `WM_QUERYENDSESSION` instead (SetConsoleCtrlHandler documentation). `CTRL_CLOSE_EVENT` (its console host closing) would still end it, so the blocker detaches from its console (`FreeConsole`).
- `SetProcessShutdownParameters(level)`: higher levels are asked first; 0x300-0x3FF is the "first" application range, the default is 0x280. The blocker sets 0x3FF so it is asked before the processes it needs (`wsl.exe`, the `down.ps1` it starts).
- Fast Startup (`HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Power\HiberbootEnabled`, read without elevation: **1** on this laptop) makes "Shut down" log the user session off and hibernate only the kernel session; the logoff still sends `WM_QUERYENDSESSION` to the user's windows, and "Restart" is always a full shutdown. Event 1074 (User32) is logged for both (three recent 1074 events were readable from the System log without elevation on this laptop).
- SpiralPool's `scripts/windows/wsl2-shutdown-hook.ps1` (BSD-3-Clause, Copyright (c) 2026 Spiral Pool Contributors, [repository](https://github.com/SpiralPool/Spiral-Pool)) registers a Task Scheduler entry on Event ID 1074 plus a sleep trigger and stops its services in WSL through `wsl -u root`. 6b is modelled on that idea: credited here. **No SpiralPool code is copied or adapted** (the task XML and script are written for ossbot), so no third-party notice file is needed. Differences: no sleep trigger (Kernel-Power 42; the VM freezes and resumes safely, §13.5), no copy of a helper into `%APPDATA%` (script and log stay in the repo), and the task runs `down.ps1`, not a service list.

## Decision
### (a) Shutdown blocker (primary, CR-001 6a)
- `scripts/windows/ossbot-shutdown-blocker.ps1` compiles `scripts/windows/ShutdownBlocker.cs` at runtime with `Add-Type` (C# 5, nothing checked in as a binary, nothing copied out of the repo) and runs one window: title `ossbot shutdown blocker`, borderless 1x1 at (-32000, -32000), `WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE` without `WS_EX_APPWINDOW` (not in the taskbar or Alt+Tab), `WS_VISIBLE`, top-level with no owner.
- On `WM_QUERYENDSESSION` (shutdown, restart or sign-out; the lParam is logged): `ShutdownBlockReasonCreate("ossbot: stopping safely…")`, then `scripts\down.ps1 -Timeout 90 -Caller blocker` (kind `graceful`, so `status.ps1` shows "graceful (a)") while the window keeps pumping messages, hard cap 90 + 90 + 30 s (the child is killed after that), then `ShutdownBlockReasonDestroy` and return TRUE: the session ends without a further click. While a down runs, a second query is answered 0 (still blocking). The user can always pick "Shut down anyway".
- `WM_ENDSESSION(FALSE)` (the shutdown was cancelled after ossbot went down) is logged: ossbot stays down until `scripts\up.ps1` or the next logon. Bringing it back automatically is not in DESIGN revision 5 (open question for FEAT-011, findings).
- Single instance per session: named mutex `Local\ossbot-shutdown-blocker` (a second start exits 0). Log `.ossbot-local\shutdown-blocker.log`, state `.ossbot-local\shutdown-blocker.state` (pid, hwnd, phase idle|stopping|released|ending, reason_active, down_exit).
- Started at logon by the second action of `ossbot-autostart` (`conhost.exe --headless powershell.exe -NoProfile -ExecutionPolicy Bypass -WindowStyle Hidden -File <repo>\scripts\windows\ossbot-shutdown-blocker.ps1`), with the task's execution time limit `PT0S` so Task Scheduler never ends it (the headless console host waits for the blocker, so the task shows `Running` for the whole session; checked live: started through the task, the blocker came up and kept running); bootstrap's `autostart` phase also starts it at once when it does not run. `kill.ps1 -Hard` still disables the task (the running blocker then finds the distro stopped and lets the shutdown go on at once).
- `down.ps1` and `up.ps1` serialise on `Local\ossbot-lifecycle`, so 6a and 6b firing during the same shutdown never run two downs (FEAT-008 item 39).

### (b) Event task (backup, CR-001 6b)
- Scheduled Task `ossbot-shutdown-hook`, registered from XML built in `scripts/lib/common.ps1` (`Get-OssHookTaskXml`): one `EventTrigger` with the subscription `*[System[Provider[@Name='User32'] and EventID=1074]]` on the System log (shutdown or restart initiated, including Windows Update restarts); no sleep trigger. Principal: the logged-on user's SID, `InteractiveToken`, `LeastPrivilege` (registered and run without elevation: `wsl -u root` needs no admin). Action: `conhost.exe --headless powershell.exe ... -File <repo>\scripts\down.ps1 -Timeout 20 -Kind hook -Caller hook`; `ExecutionTimeLimit PT2M`, `IgnoreNew`, hidden, no battery conditions. Script and log stay in the repo.
- Windows does not wait for scheduled tasks during a shutdown, so 6b is best effort. User32 1074 is logged when the shutdown starts, usually a moment before the blocker gets `WM_QUERYENDSESSION`; a hook `down.ps1` waits 3 s when the blocker runs, so the primary path (90 s drain) normally takes the lifecycle mutex first and the hook then finds the distro stopped and exits 0.
- `bootstrap.ps1` phase `shutdownhooks` installs 6a (the autostart action, starting the blocker if needed) and 6b; `bootstrap.ps1 -Uninstall [-Only shortcuts,shutdownhooks,autostart,hyperv,wsl]` (implemented by `scripts/uninstall-host.ps1`) removes only the ossbot-* tasks, the blocker, the shortcuts and the documented host files; `-Uninstall -Only shutdownhooks` keeps `ossbot-autostart` with its distro-boot action. `bootstrap.ps1 -Shortcuts` adds the Start-menu shortcuts "ossbot Up/Down/Status/Kill" (`%APPDATA%\Microsoft\Windows\Start Menu\Programs\ossbot\`, Windows PowerShell `-NoExit` on the repo scripts); off by default.
- `scripts\ossctl.ps1 doctor` checks the autostart task (both actions, `PT0S`), that the blocker runs with a visible window, the hook task against its spec (trigger subscription, action, run level, `PT2M`) and reports Fast Startup.

Live (2026-10-19, not elevated): the event-trigger task registered as this non-admin user (DESIGN §23 item 31, last part: verified); `Start-ScheduledTask ossbot-shutdown-hook` stopped the distro in 20.9 s (the 3 s yield to the running blocker plus a 17 s down), task result 0, `status.ps1` then showed last shutdown `hook`; `-Uninstall -Only shutdownhooks` and a re-install worked, the second install run printed only `unchanged`.

## Observations on this laptop (simulated, 2026-10-19; Windows was not shut down)
`tests/system/test_shutdown_blocker.ps1` sends `WM_QUERYENDSESSION` to the blocker's window with `SendMessageTimeout` from another process: the window is visible, top-level, off-screen and a tool window (exstyle 0x8010080); the reason was created and read back on the window thread (`query='ossbot: stopping safely…'`) 0.6 s after the message; `down.ps1` ran (12.5 s, exit 0, the distro stopped, marker graceful); the message returned TRUE only then (13.1 s); the reason was destroyed (`query=none`); `WM_ENDSESSION(FALSE)` was logged and the blocker kept running; `up.ps1` showed last shutdown `graceful`.

Still to verify on a real restart (DESIGN §23 item 31, FEAT-011 item 57, needs the user): that Windows lists the off-screen tool window with its reason in the blocking screen, that the shutdown continues by itself once the reason is destroyed and TRUE is returned, the behaviour of "Shut down" with Fast Startup on (expected: the logoff sends the query), and that `wsl.exe` keeps working while the session is ending.

## Consequences
- A graceful stop costs up to the drain time at shutdown; the user sees "ossbot: stopping safely…" and can skip it.
- Windows may still end the process (forced restart, power loss, "Shut down anyway"); crash safety (§13.5 (c)) covers that.
- The blocker is one more per-user process at logon (no window in the taskbar). `bootstrap.ps1 -Uninstall` removes it with the tasks.

## Implementation addendum (post-v1, 2026-10-20): drain channel, 6b retired

### Evidence
Three real shutdowns/restarts on this laptop (2026-10-20 03:08, 14:38 and 14:46 UTC, `.ossbot-local\shutdown-blocker.log`): the blocker created its block reason, then started `powershell.exe -File down.ps1`. The child died in 0.0 s with exit -1073741502 (0xC0000142, STATUS_DLL_INIT_FAILED), nothing drained, and the next boot recorded `unclean`. The 6b task's last result was 3221226091 (0xC000026B, STATUS_DLL_INIT_FAILED_LOGOFF). The earlier "passes" (2026-10-19) were cancelled shutdowns, where the session kept running.

### Research (checked 2026-10-20)
- R1, a new process at shutdown time. Microsoft Learn, "User32.dll or Kernel32.dll does not initialize" (https://learn.microsoft.com/en-US/troubleshoot/windows/win32/user32-kernel32-not-initialize): a new process fails DLL initialisation when it cannot reach its window station and desktop. Chromium issue 542224257 (https://issues.chromium.org/issues/542224257, snippet only): when Windows ends a session it refuses to initialise new processes (children exit with 0xC000026B, CreateProcess fails with ERROR_SHUTDOWN_IN_PROGRESS 1115). Secondary: https://github.com/deepseek-ai/deepseek-harness/discussions/8878 (a console child of a console-less parent needs a new conhost; when that fails it dies with 0xC0000142).
- **Launching `wsl.exe` directly with CREATE_NO_WINDOW at shutdown: evaluated and rejected.** `wsl.exe` is also a console-subsystem image. Started from the console-less blocker it needs a new conhost and a fresh user32/kernel32 initialisation against a desktop that is being torn down, the same steps that failed for `powershell.exe`. No source says a console image starts reliably in an ending session; the expected result is the same 0xC0000142 (or 0xC000026B, or 1115). It was not tried on a real shutdown, because the result would not change the design.
- R2, a SYSTEM-context or other-session task for 6b. Microsoft Q&A "Unable to start WSL from a Scheduled Task" (https://learn.microsoft.com/en-us/answers/questions/1184579/unable-to-start-wsl-from-a-scheduled-task), microsoft/WSL issues 3918 (https://github.com/Microsoft/WSL/issues/3918) and 10732 (https://github.com/microsoft/WSL/issues/10732): WSL started from a task that is not the interactive user's does not work reliably unless the account is an administrator, and Store distros fail. A SYSTEM task runs in session 0, so the logoff of session 1 would not hit it with 0xC000026B, but SYSTEM cannot reach this user's per-user distro, registering a SYSTEM or S4U task needs elevation (bootstrap runs without it), and Task Scheduler does not wait for tasks during a shutdown anyway. A same-session task hits the logoff refusal, as observed.

### Decision
- **No process is created at shutdown time.** At start the blocker opens one long-lived drain channel: `wsl.exe -d ossbot -u root --exec /opt/ossbot/app/.venv/bin/ossctl drain-listen`, hidden (`CreateNoWindow`, `UseShellExecute=false`), stdin/stdout/stderr redirected and kept. Its conhost already exists, so at shutdown only a pipe write is needed. `ShutdownBlocker.cs` has one `Spawn()` helper, which refuses (and logs `spawn refused`) for the whole `WM_QUERYENDSESSION`.
- **Channel health.** A 1 s timer reads pongs and notices a dead child at once; every 60 s it pings the live channel (two unanswered pings restart it). A dead channel is restarted only when `wsl.exe -l --running -q` lists the distro, run asynchronously at normal times and never during a query, so the blocker never starts the distro and a manual `down.ps1` stays down until `up.ps1`. Log lines: `channel started|restarted pid=…`, `channel up pid=… pong=<lifecycle>`, `channel died exit=…`, `channel skipped: distro stopped`; the state file carries `channel`, `channel_pid`, `channel_pong`, and `status.ps1` / `ossctl.ps1 doctor` show them.
- **Listener** (`src/ossbot/ctl/drain_listener.py`, hidden command `ossctl drain-listen`, root only, from the root-owned deployed copy). A fixed, stop-only grammar (I8/I9; nothing can express a go action), one ASCII line of at most 64 bytes:
  - `ping` → `pong <lifecycle-state>`;
  - `down <0..120> <caller [A-Za-z0-9_-]{1,40}>` → `ack`, then `run_down(timeout, "graceful", "distro")` in-process (the function `ossctl down` itself calls), then `drained exit=<n> elapsed=<s>`;
  - anything else → `error grammar`, ignored.
  After `down` it ignores SIGHUP and SIGPIPE and finishes the drain even when stdin or stdout closes. EOF otherwise ends it. It never touches the kill/pause flags; markers are unchanged (`shutdown-marker {type: graceful}`, so the next boot shows `graceful`). Its stdout is the channel only (fd 1 is pointed at stderr for the down path).
- **At `WM_QUERYENDSESSION`** the blocker creates the reason, takes `Local\ossbot-lifecycle` (≤ 5 s, then drains anyway), writes `down kind=graceful caller=blocker pid=<pid>: start timeout=90 (channel)` to `lifecycle.log`, sends `down 90 blocker`, pumps messages until `drained` (cap 90 + 30 s), logs `ossctl-exit=` and `end exit=` in the down.ps1 format, destroys the reason and returns TRUE. With no live channel it logs `no channel (distro stopped or listener dead): nothing to drain` and returns TRUE at once. `wsl --terminate` is dropped at shutdown: the VM stops with Windows, after the marker is written.
- **6b retired.** `bootstrap.ps1 -Only shutdownhooks` removes a registered `ossbot-shutdown-hook` (`Remove-OssHookTask`); status and doctor report `retired (control channel)`. `down.ps1 -Kind hook` stays valid for manual tests. This replaces DESIGN §13.5 (b) "both (a) and (b) are required": (b) could never work at a real shutdown, and the channel is the only path that does not start a process in the ending session.
- `status.ps1` renders `last shutdown` from the record's own fields: `unclean (no shutdown marker: ossctl down did not run; detected …)` instead of the old "unknown (ossctl status gave no data)".

### What R1 must still show (owner, real restart)
Only a real restart proves that the already-running `wsl.exe` and the VM live long enough for the drain. Expected: "ossbot: stopping safely…" in the blocking screen, the blocker log `channel: sent down 90 blocker`, `channel: ack`, `channel: drained exit=0`, the session continuing by itself, and after logon `status.ps1` showing `last shutdown graceful`. If the channel's `wsl.exe` is ended before `drained`, the listener still finishes the drain (SIGHUP ignored), and the marker shows whether it did. Steps: docs/FINAL_REPORT.md R1.
