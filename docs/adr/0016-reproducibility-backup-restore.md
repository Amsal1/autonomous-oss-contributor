# ADR-0016: Reproducibility: bootstrap from zero, state-outside-git inventory, encrypted backup/restore
Status: Accepted · Date: 2026-10-17 · Design: DESIGN.md §18.2, §18.7, §18.8

## Context
The user wants to rebuild from a fresh Windows install with `git clone` + scripts, and to keep history (audit log, contributions, Hermes memory) across reinstalls. v1 assumed the `ossbot` distro already existed and had no backup story. WSL 3.0.3 `wsl --help` (checked locally) offers `--install <Distro> --name --location --no-launch` and `--import-in-place <Distro> <vhdx>`.

## Decision
- `bootstrap.ps1` is idempotent from zero: if `ossbot` is not registered it runs `wsl --install Ubuntu-24.04 --name ossbot --location <repo>\.wsl\ossbot --no-launch` and provisions as root; if an orphaned `ext4.vhdx` exists it offers `--import-in-place` instead of creating a second disk. It never unregisters or deletes a distro or VHD.
- SETUP.md is the DR runbook (install WSL, clone, profile, bootstrap, credentials or restore, doctor, go live, routine, uninstall, troubleshooting).
- The design keeps an explicit inventory of state outside git with its recovery path.
- `ossctl backup` (root; `scripts/backup.ps1`): pauses, copies the DB with SQLite's online backup API, verifies the audit chain against anchors, builds a tar + manifest, encrypts with `age` to X25519 recipients from the profile (always encrypted; recipient keys let a weekly timer run without storing a secret), writes `backups/ossbot-<ts>.tar.age` (gitignored), keeps 8. Secrets and artifacts are opt-in flags.
- `ossctl restore`: kills first, decrypts with an identity streamed from Windows, verifies manifest and audit chain, moves current state aside (never deletes), installs with correct owners/modes, forces dry-run ON and stays killed until the human resumes; open approvals invalidated.
- Not backed up: Docker data/images (rebuilt), sandboxd subnet DB, the VHDs (the user may copy them while the VM is stopped), Kiro device-flow login state.

## Consequences
The user must keep the age identity safe outside the machine; losing it makes archives unrecoverable (documented). **Verify:** fresh-install WSL command, `--no-launch` distro usable as root before any OOBE user, `age -d -i -`, Hermes state layout for the include list.

## Implementation addendum (FEAT-008 item 43, 2026-10-19)
- **age (DESIGN §23 item 26, verified):** latest release v1.3.2 (2026-08-29), `age-v1.3.2-linux-amd64.tar.gz` sha256 `cbe24006…26ac10` (release asset digest), pinned in `config/versions.lock.yaml` and installed by the `apt-base` step as `/usr/local/bin/age` and `age-keygen` (`download_verified`). age(1) at v1.3.2: `-i -` reads the identities from standard input, the archive must then be a file argument; a passphrase-protected identity file is accepted and its passphrase is asked interactively (from the terminal). v1.3 also has post-quantum hybrid recipients (`age1pq1…`); classic and hybrid recipients cannot be mixed in one file, so `ossctl backup` refuses a mixed list. Live: the roundtrip test decrypted with an identity on stdin.
- **Include list:** §18.8 plus the Hermes state. For Hermes the rule of §18.8 ("`.hermes/` minus code and caches") is applied as an exclude list (`HERMES_EXCLUDE` in `ctl/backup.py`: `hermes-agent`, `installs`, `tools`, `plugins`, `hooks`, caches, `logs`, `kiro-cwd`, `.env`, locks and the gateway's runtime files), because the live layout has more state than the FEAT-007 list (cron, kanban, shared-state, state dirs); everything in the FEAT-007 list (config.yaml, SOUL.md, memories, sessions, state.db, response_store.db, skills = the active skills, pending, ossbot-features = the feature stores) is kept. The root skill gate state `/var/lib/ossbot/skills` and `config/telegram.yaml` (when present) are in; chat attachments only with `--include-attachments`; secrets with `--include-secrets` or `policy.backup.include_secrets`. Every SQLite file (gatekeeper and Hermes) is copied with the online backup API and the anchors before the DB (an anchor never names a row the copy lacks).
- **Archive:** tar of `MANIFEST.json` (format 1; per file path, item, sha256, size, mode, owner, group; directories and sibling-name symlinks) and `files/<absolute path>`, encrypted with age; the plaintext only ever exists in a 0700 dir under `/var/tmp` (ext4) and is removed before the command returns. `POST /v1/audit/backup-created` records `backup_created` (metadata only); with the gatekeeper down the event is appended directly.
- **Pause and resume:** the backup pauses through the API (reason `backup`) and lifts only its own pause with `ossbot-resume --offline --via backup --paused-only` (removes `paused` only; a kill that arrived meanwhile stays), and not at all when anyone paused, killed or resumed in between. The resume.log line has `paused_only: true`; reconcile does not treat such a line as evidence of a removed kill flag (P1-7), so a backup does not invalidate armed approvals.
- **Restore:** soft kill (reason `restore`), every unit holding state stopped (workers, gatekeeper, proxy, watchdog and the skills/tier timers; the boot gate, firewall units and Docker filter stay), identity on stdin only (`--identity -`; `scripts/restore.ps1` reads the Windows file and streams it), manifest checks (known format, no member outside the manifest, every listed file present, regular files only, each target inside its item, no setuid, setgid only on directories, sha256 and size), the current items moved to `/srv/ossbot/restore-previous-<ts>/` (with their SQLite siblings; `chattr -a` on the anchors for the move, `+a` after the install), the recorded owners and modes applied (also on the drvfs `config/profile.yaml`: found live that a root-created 0600 profile locks the gatekeeper out and lets the watchdog pause), migrations, audit verify, all open approvals of the three decision services invalidated (`restored`), `dry_run = 1`, state killed, the resume.log offset moved to the current end, one `restored` event; then the gatekeeper and proxy start in killed mode for `/resume`. A refused archive is refused before anything is moved or written.
- **Live (2026-10-19):** `tests/system/test_backup_roundtrip.sh` with a throwaway identity under `/root/.cache/ossbot-test`: all 38 checks passed (see VERIFICATION). With the owner's profile (`age_recipients: []`) `ossctl backup` refuses with exit 2 and does not pause. `ossbot-backup.timer` is installed and disabled.
- **Review round 1 fixes (2026-10-19):** backup and restore run as root on directories other uids own, so neither reads or writes through a symlink: an item root that is a symlink or has one above it (`realpath` differs), a Hermes home that is not a real directory of `hermes` or is replaced during the copy, and a file whose opened fd resolves elsewhere abort the backup; restore checks the same after the units are stopped and refuses with nothing moved (`ctl/backup.py` `path_problem`, `Layout.hermes_home_problem`; `ctl/restore.py` `check_targets`). Restore also refuses before decrypting when the kill wrote no flag or a unit did not stop. `ossbot-resume --paused-only` starts no unit, so a backup during a workers down leaves runner, Hermes and sandboxd stopped. Live: the roundtrip test (45 checks, incl. the workers-down case) passed.
- **Limits:** a passphrase-protected identity cannot be used through `restore.ps1` (no terminal on the stdin stream for age's prompt); use an unprotected copy for the restore. The restore rolls the DB back to the archive's moment (by design).

## Implementation addendum (post-v1, 2026-10-21): retention and housekeeping

Context: the distro VHD had grown to 22 GiB and nothing expired logs, Docker cache or DB rows. Owner decisions: time-based retention only (no journal or build-cache size cap), journal entries older than 30 days are useless, unused Docker build cache is pruned from time to time. DESIGN §18.10 is the normative description.

Decisions:

- **D1 Who deletes what.** The gatekeeper deletes its own DB rows and its 0700 dirs (`gatekeeper/retention.py`), triggered only by the operator-only `POST /v1/retention/run`: it is the single writer of its SQLite file (WAL, triggers, audit chain), and a root process writing it would race the live service. Root deletes the root-reachable stores in `ossctl gc` (`ctl/gc.py`): `/tmp`, artifacts, run logs, Hermes' `sessions/`, Docker, fstrim. Root helpers are TCB (I2) and already handle Docker and the Hermes home. sandboxd and the Docker filter gain no endpoint and no rule.
- **D2 Artifacts eligibility comes from the gatekeeper.** Root deletes `/srv/ossbot/artifacts/<cid>` only for the `eligible_cids` of the retention report (terminal for `contributions_days`, no open action or approval), after the cid pattern, lstat (a real dir) and containment checks. Unknown dirs (the `sys-*` pseudo cids included) are never deleted.
- **D3 Hermes sessions.** Regular files directly in `~hermes/.hermes/sessions/` idle for `hermes_sessions_days` (90), except `sessions.json` and `*.jsonl` (V5). `state.db`, memories, skills and everything outside the dir are never touched, so sessions stay resumable.
- **D4 Docker.** Dangling images minus an explicit keep set (every `ossbot/*` tag, the `images:` digests and `ubuntu@<base_images.ubuntu_24_04>` of the root lock copy), removed one by one with `docker image rm` (no `--force`, an image in use is refused); afterwards every keep ref that resolved before must resolve to the same id, else the store FAILs. Not `docker image prune`. Build cache: `docker builder prune --all --force --filter until=<docker_build_cache_hours>h`, weekly; `--build-cache-until-hours 0` drops the filter for a one-off.
- **D5 Journal.** A tracked drop-in `MaxRetentionSec=30d`, `MaxFileSec=1week`, no `*MaxUse`/`*KeepFree` key; journald enforces it itself, also while gc is skipped because of a kill.
- **D6 Kill gate.** Both units carry `ConditionPathExists=!/var/lib/ossbot/control/killed` and `!…/paused`; the `ExecCondition=--allow minimal` variant is not used because it lets a soft kill through. `ossctl gc` re-reads both flags before every store and every deletion and stops with exit 3; `ossbot-kill` stops both units at both levels; the gatekeeper endpoint answers 409 while killed or paused.
- **D7 Config.** `policy.yaml retention:` (`RetentionPolicy`, `extra="forbid"`, bounded), read from the config snapshot by the gatekeeper, `ossctl gc` and doctor; no snapshot = `ossctl gc` exits 2 and deletes nothing.
- **Safety of the root deleter.** Every store root is opened from `/` one component at a time with `O_NOFOLLOW` (a symlinked `sessions/`, `.hermes` or artifacts root fails the store instead of being followed), entries are single names below that fd, re-checked and deleted relative to it (`shutil.rmtree(dir_fd=…)`, the fd-based implementation), so hermes, ossbox or any `/tmp` user cannot redirect a root deletion. The JSON report lists entry names for the operator (never Hermes file names); the journal gets counts and bytes only.

[VERIFY] results (2026-10-21; fetched pages treated as data):

- **V1 build cache prune** (Docker 29.9.1, buildx v0.38.0 `0dbe87f`). [docs.docker.com: docker buildx prune](https://docs.docker.com/reference/cli/docker/buildx/prune/): `until` keeps records used within the duration (so it is measured against last use, not creation); `--all` adds the internal and frontend (`#syntax=`) images; records in use are not reclaimable. Live: `docker builder prune --help` is the buildx prune (same flags); `docker buildx du --verbose` shows `Created at`, `Usage count` and `Last used` per record; 9.432 GB reclaimable on the day, records last used 13 h to 3 days ago.
- **V2 dangling images.** `docker info`: image store = containerd snapshotter (`driver-type io.containerd.snapshotter.v1`, overlayfs). `docker image ls --filter dangling=true --digests` listed nothing; the digest-pinned base shows as `ubuntu <none> sha256:68ee2200…` but is not dangling, and its image id equals the pinned index digest (as do the `ossbot/*` ids and the lock digests), so the keep set matches by id. The base image and the current images are never prune candidates; the post-check guards a future store change. No stop needed.
- **V3 journald** (systemd 255.4-1ubuntu8.18). [journald.conf(5)](https://www.freedesktop.org/software/systemd/man/latest/journald.conf.html): `MaxRetentionSec=` deletes journal files whose entries are older than the span (default 0 = off) and needs no size key; `MaxFileSec=` rotates files after the span (default one month), so with one week files expire in at most 30 d + 1 week. Drop-ins in `/etc/systemd/journald.conf.d/*.conf` are read at start, hence the restart. Live: `systemd-analyze cat-config systemd/journald.conf` had only `ForwardToSyslog=yes` (rsyslog's `/var/log/syslog` keeps its own logrotate rotation); `journalctl --disk-usage` 775.7 MiB before the drop-in.
- **V4 fstrim in WSL2.** [WSL settings (learn.microsoft.com)](https://learn.microsoft.com/en-us/windows/wsl/wsl-config): `sparseVhd=true` makes newly created VHDs sparse ([disk space](https://learn.microsoft.com/en-us/windows/wsl/disk-space)). Live: `lsblk --discard` shows discard support on `/dev/sdd` (granularity 1M, max 4G); `/` is mounted with `discard` (online discard); `config/wsl/wslconfig` has `sparseVhd=true`; `ext4.vhdx` 22.38 GiB logical, 21.88 GiB on disk (`GetCompressedFileSizeW`) with `df` 20.3 GiB used, so the file is sparse and the logical length is a high-water mark that does not shrink. `fstrim -v /` (util-linux; `-n` dry run exists) runs last in each live pass; the before/after on-disk measurement is the close-out's.
